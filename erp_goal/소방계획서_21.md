## #1 계획서 공통문구 — 한곳에서 관리

상태: **기안 완료, 구현 전** · 결정 7건(D-1~D-7) 확정 · **재검토 1회 반영(2026-08-12)**

### 착수 전 조사 — "다른 고객도 가져오기"는 이미 된다

| 확인 사항 | 사실 |
|---|---|
| 라이브러리 테이블 | `plan_text_library`(마이그레이션 119)에 **`customer_id`가 없다 — 전역 테이블**. 한 고객이 등록한 문구를 다른 고객이 [공통에서 가져오기]로 쓰는 건 이미 동작 |

### 진짜 공백 = 관리 진입점

- 어느 섹션에 무엇이 등록돼 있는지 **전체를 조망할 수 없다**
- 전역 데이터인데 **고객을 하나 열어야만** 관리 가능하다
- 8섹션을 훑으려면 서식을 8번 이동해야 하고, **기본항목이 비어 있는 섹션을 찾을 방법이 없다**
  (기본항목이 없으면 신규 고객 자동주입이 조용히 아무 일도 하지 않는다)

즉 이 요구는 `소방계획서_15_별도라이브러리` 로드맵의 **R-3(라이브러리 관리 페이지, deferred)** 를 실행 항목으로 승격하는 것이다.

### 결정 (2026-08-12 사용자 확정)

- **D-1**: 관리 화면에서 **8섹션 전부 본문 직접 편집**을 허용한다. (대안 "서술형 4섹션만"·"조회 전용" 기각)
- **D-2**: 권한은 **현행 `customer_manage`(전 직원) 유지**. 지금도 서식 팝오버에서 전 직원이 삭제·기본지정을 할 수 있어, 관리 화면은 *가시성*만 추가한다. 대신 삭제·기본변경 시 **사용처 건수를 함께 보여** 실수를 줄인다.
- **D-3**: 사이드바 **소방안전관리 그룹 맨 아래 `계획서 공통문구`**(점검표 관리 옆). 파일에 명시된 "마스터데이터는 맨 아래" 순서 규칙과 일치.
- **D-4**: 관리 화면에 **'n명에게 일괄 반영' 버튼을 만들지 않는다.** 119 설계가 "즉시 일괄 덮어쓰기는 하지 않는다"고 못박은 이유(이미 제출된 HWP·PDF와의 불일치, 고객별 수정분 유실)가 그대로 유효하다. 개정 반영은 R-1에서 **고객 쪽 배지 + 1클릭**으로 다룬다.

**재검토로 추가된 결정 (2026-08-12)**

- **D-5**: 화면을 **3단 트리가 아니라 "표준 계획서 한 장"(단일 세로 문서 + 좌측 목차)** 으로 만든다.
  *기각 사유*: ① 규모가 작다 — 8섹션 × 소수 항목이라 전체 10~25개다. 트리는 감출 것이 많을 때 이득인데 여기엔 감출 것이 없고 클릭만 늘어난다. ② **작업 패턴이 맞지 않는다** — 이 화면에서 가장 잦은 일은 *도입 시 8섹션 채우기*와 *기본문구 고치기*인데, 트리는 한 번에 한 항목만 보여준다. ③ 트리는 `⭐기본문구`와 대안 문구를 **같은 층위의 형제**로 놓아 주인공이 묻힌다.
  단일 문서는 도입 시 위에서 아래로 한 번 훑으면 끝나고, 빈 섹션이 스크롤만으로 드러나며, **개발량도 원안보다 작다**(트리 컴포넌트와 '상세 3상태'가 하나로 합쳐진다). 모바일에도 유리하다. 사용자가 말한 "트리형식"의 의도(한곳에서 계층적 조망)는 좌측 목차가 수행한다.
- **D-6**: **`[고객에서 불러오기]`와 `[복제]`를 1단계에 넣는다.** (원안은 R-4로 2단계였음)
  빈 화면에 8섹션을 타이핑하는 것보다 **이미 잘 작성된 고객 하나를 골라 8섹션을 통째로 승격**하는 편이 압도적으로 빠르고, 기존 `pick`을 그대로 태우면 되어 구현이 싸다. 복제(아파트용 → 오피스텔용)도 `getPlanText`+`savePlanText` 조합이라 신규 액션이 필요 없다.
- **D-7**: 문구 안 **치환 변수(`{{고객명}}` 등)는 보류하고 실태 조사만** 한다. 미치환 시 제출 문서에 `{{고객명}}`이 그대로 인쇄되는 위험이 있어, 현재 고객들의 서술에 고객명·건물명이 실제로 얼마나 박혀 있는지 확인한 뒤 판단한다.

### 설계

**위치**: 전역 페이지 `/fire-plans/library` 신설. 데이터가 전역이므로 고객 종속 화면(소방계획서 트리)에 두지 않는다 — 같은 데이터가 모든 고객 화면에 중복 노출되고, 거기서 누른 삭제가 전사 삭제라는 사실이 화면 맥락과 어긋난다. `fire-plans/` 세그먼트에 `page.tsx`가 없어 충돌 없음.

**진입 동선 3개**: ① 사이드바 ② 서식 팝오버 하단 `전체 관리 ↗`(새 탭 · `?section={key}` — 같은 탭 이동은 미저장 확인창과 부딪힌다) ③ 상세의 사용처 목록 → `/customers/{id}?tab=plan&form=1.11` 딥링크(기존 `form=` 쿼리 재사용).

**화면 — "표준 계획서 한 장"** (D-5). 8섹션을 세로로 이어 놓고 **각 섹션의 `⭐기본문구`가 처음부터 펼쳐진 채 편집 가능**하다. 좌측 목차는 점프용이고, 대안 문구는 섹션 헤더의 드롭다운으로 접어 둔다.

```
📚 계획서 공통문구      [고객에서 불러오기]  [+ 새 항목]   기본 6/8

┌ 목차 ─────┐  ┌────────────────────────────────────────────┐
│ 📘 1장     │  │ 1.11 훈련·교육   ⭐아파트용 표준 ▾  v3 · 사용 12 │
│   1.11 ⭐  │  │                          [복제] [⭐] [삭제] [저장] │
│   1.12 ⭐  │  │  시나리오 유형 ( 주택형 ▾ )                     │
│   1.13 ○  │  │  시나리오   [................................] │
│   1.14 ○  │  │  차수별 세부계획 (서술만)              [+ 행]   │
│   1.15 ⭐  │  │  ※ 일시·장소·인원·실시결과는 고객 고유 — 미저장  │
│ 👥 2장 ⭐  │  ├────────────────────────────────────────────┤
│ 🚪 3.4 ⭐  │  │ 1.13 소방시설 공사·정비                        │
│    3.6 ○  │  │  ⚠ 기본 미지정 — 신규 고객에 자동으로 채워지지   │
└───────────┘  │     않습니다                    [지금 작성]     │
               └────────────────────────────────────────────┘
```

- 좌측 목차 = 장 → 섹션 2단(점프 링크). 섹션마다 `⭐` 또는 `○`를 달아 **기본문구가 비어 있는 섹션을 한눈에** 드러낸다 — 이 화면의 최대 가치다.
- 각 섹션은 **독립 저장**(고객 서식과 같은 방식)이라 한 섹션을 고치다 다른 섹션으로 옮겨도 미저장 처리가 단순하다.
- 대안 문구는 헤더의 `⭐아파트용 표준 ▾` 드롭다운으로 전환하고, 전환한 항목에 `[⭐ 기본으로]`를 눌러 승격한다.
- 섹션마다 **어떤 필드가 공통 대상인지 명시**한다(1.11은 시나리오·세부계획 서술만, 일시·장소·인원은 고객 고유라 저장되지 않음).
- 하단에 사용처 목록(고객명 / 가져오기·자동주입 / 가져간 version / 적용일 / 딥링크). 가져간 version이 낮으면 앰버 `개정됨` 배지 — **조회 전용**(D-4).

**[고객에서 불러오기]** (D-6): 고객 선택 → 그 고객의 8섹션 `pick` 결과를 미리보기 → 체크한 것만 이름을 붙여 등록(원하면 `⭐기본`까지 한 번에). **도입 시 8섹션을 한 번에 채우는 가장 빠른 길**이다.

**본문 직접 편집** — 기존 서식 컴포넌트는 재사용 불가다. props가 `customerId`에 묶여 있고 저장을 스스로 호출하며, 라이브러리에 있으면 안 되는 UI(인원 칸·월 그리드·결과 기록부·`LibraryTextButton` 자기 자신)를 품는다. 대신 라이브러리 body의 실제 모양이 **두 가지뿐**이라는 점을 쓴다:

| 모양 | 섹션 | 렌더 |
|---|---|---|
| `Record<고정키, string>` | 2장 팀별임무(7키) · 3.6 피난약자(6키) · 3.4 procedure · 1.11 시나리오 | 라벨 + textarea 반복 |
| `Row[]`(텍스트 열 N개) | 1.12~1.15 기록부(각 2열) · 1.11 세부계획(6열) | 행 추가/삭제 + input 반복 |

→ `PlanTextSectionDef`에 `chapter`·`editor` 스펙을 **순수 추가**하고 공용 렌더러 하나가 8섹션을 모두 담당한다. 필드 취사선택이 `plan-text-sections.ts` 한 곳에만 존재한다는 **기존 단일 원천 규약이 유지**된다.

**저장 액션은 신규가 필요 없다** — `savePlanTextAction`이 서버에서 다시 태우는 `pick`(`pickRows`·`pickRecord`)이 **멱등**이라, 편집한 body를 그대로 넘겨도 동작한다. `planTextBodyEquals` 덕에 내용 무변경 저장 시 version도 오르지 않는다. 단 **이름 변경은 반드시 `renamePlanTextAction`으로만**(version 미증가 규약).

## #2 계획서 생성·조회 재편 — 두 버튼의 정체와 자동화

상태: **기안 완료, 구현 전** · 결정 7건(D-1~D-7) 확정

### 1번 질문의 답 — 두 버튼은 사실상 같고, 라벨이 거짓이다

| | 트리 상단 `계획서 생성 (HWP+PDF)` | 보관함 `계획서 생성 (PDF)` |
|---|---|---|
| 호출 | `requestFirePlanHwpFromTabAction` | **동일** |
| 산출물 | HTML + PDF | **동일** |
| 유일한 차이 | 용도 기반 **프리셋 적용**(`recommendPresetType(purpose)`) | 프리셋 미적용 |

**HWP는 만들어지지 않는다.** `fire-plan-generate.ts:463-464`가 `hwp_name: null, hwp_path: null`을 넣고, 같은 파일 주석이 "§6: hwp_path는 신규 기록하지 않는다"고 못박는다. 소방계획서_7 **H-13(2026-08-04)** 이 한글 SDK·워커 경로를 걷어내고 HTML→Gotenberg 단일 경로로 바꿨는데 **라벨과 툴팁만 남았다** — `plan-tab-view.tsx:314`는 아직 "워커(한글 SDK)가 HWP+웹 미리보기+PDF를 보관함에 등록"이라고 이미 없어진 동작을 설명한다.

즉 질문의 답은 **"차이는 프리셋 하나뿐이고, HWP는 나오지 않으며, 라벨이 사실과 다르다"** 이다.

### 2번 질문 — 진짜 문제는 버튼 개수가 아니다

현행 구조는 **보려면 파일이 있어야 하고, 파일을 만들면 개정차수가 오른다**:

- 미리보기 = 저장된 `html_path`를 연다 (`fire-plans-client.tsx:188`)
- 인쇄 = 저장된 PDF를 연다 (`:197`)
- 그 파일은 `generateFirePlanNow`가 **새 행 + `revision +1` + 개정이력 행**을 만들 때만 생긴다 (`fire-plan-generate.ts:450-482`)

그래서 사용자는 **확인하려고 생성**하게 되고, 보관함이 초안 더미가 되며 개정이력이 오염된다. 준비율 미달이어도 생성되므로(fail-soft) 빈 칸 문서가 차수를 올려 가며 쌓인다.

**여기에 자동 생성을 얹으면 악화된다.** 서식이 12종이라 저장마다 만들면 Gotenberg를 수십 번 부르고(부분 저장 중간 상태의 PDF는 의미도 없다), 탭 진입마다 만들면 "보러 갔는데 파일이 생기는" 부작용이 난다.

**따라서 조회를 파일에서 떼어낸다.** 그러면 자동 생성 요구의 절반이 증발하고, 남는 절반(인쇄용 PDF)만 요구 시 갱신하면 된다.

### 결정 (2026-08-12 사용자 확정)

- **D-1**: 트리 상단 생성 버튼을 **제거**하고 **보관함을 남긴다.** 생성물이 쌓이는 곳에서 생성해야 결과가 그 자리에 바로 보인다 — 지금은 상단에서 만들어도 "보관함에 등록되었습니다" 메시지만 뜰 뿐 확인하려면 어차피 보관함으로 가야 한다. 생성 관련 동작(신규·행별 재생성·연차 발행)이 한 곳에 모이는 이점도 있다. **프리셋은 보관함으로 이관**한다 — 안 그러면 남는 쪽이 프리셋을 빠뜨린다.
  *기능 손실 0 근거*: 생성 바는 `plan-tab-view.tsx:285-287`에서 `sel` 조건 **바깥**에 있어 모든 서브탭 상단에 고정되고, 보관함은 `:431`의 `sel === 'archive'` 안에서 그 **아래**에 렌더된다. 즉 보관함 화면엔 같은 기능 버튼이 위아래로 둘 있다. `FirePlansClient`는 `customers/[id]/page.tsx:659`에서 오직 이 노드로만 쓰이므로 다른 화면의 유일 진입점이 되는 경우도 없다.
- **D-2**: **HWP 표기를 전부 걷어낸다.** SDK는 의도적으로 폐기됐고 자동 생성분에 HWP는 없다(업로드분만 보유).
- **D-3**: **조회 = 즉석 렌더**(파일 0). 보관함 상단 '현재 내용' 카드에서 `buildFirePlanHtml`을 그 자리에서 렌더한다. **Gotenberg 미호출**, 비용은 조립 수백 ms뿐. 별지 미리보기(`getAnnexPreviewHtmlAction`)와 같은 패턴.
- **D-4**: **[인쇄]·[PDF 받기]는 말없이 갱신한다.** 최신본이 낡았으면 **같은 행의 파일만 교체**하고 인쇄한다. 차수·개정이력 불변. 사용자는 생성을 의식할 필요가 없다 — 이것이 요구된 자동화의 실질이고, 필요할 때만 Gotenberg를 부르므로 낭비가 없다.
- **D-5**: **개정 차수는 [개정 발행] 버튼에서만 +1.** 사람이 "이 내용으로 확정"하는 순간이다. 제출하지 않는 내부 개정도 기록할 수 있다.
- **D-6**: **제출 기록이 있는 행은 동결한다.** 소방서에 낸 PDF를 다시 인쇄할 때 내용이 바뀌면 안 된다. `fire_plans.submitted_at`이 이미 있다(`fire-plans-client.tsx:167`). **이 구분이 빠지면 D-4가 위험해진다.**
- **D-7**: **stale 판정은 조립 결과 해시**로 한다. `fire_plan_forms.updated_at`(096:9)만 보면 고객·건물·시설 대장·자위소방대 변경을 놓치는데 계획서 내용의 상당 부분이 거기서 온다. 인쇄 시 어차피 조립하므로 추가 비용이 거의 없고, 해시가 같으면 Gotenberg를 건너뛴다.

### 설계 — 3층으로 나눈다

### 용어 — 축이 둘이고 코드가 섞어 부른다 (2026-08-12 사용자 정정)

### 조사 1 — 완료 판정이 두 갈래다 (요구 4-1의 정체)

타임라인의 ✓와 자체 진행률은 **증거**로 계산한다 (`inspection-timeline-client.tsx:264-270`):

```
done1 = responded > 0                 done4 = !!submit9.submittedAt
done2 = !!certFile || certArchived    done5 = hasDefects && defects.done >= defects.total
done3 = !!delivery                    done6 = !!submit11.submittedAt

*마이그레이션 128*: `message_templates`(`key`·`subject`·`body`·`attachment_name`·`updated_by`·`updated_at`) + `report_deliveries.body TEXT`. 시드로 현행 문구를 그대로 넣는다. `company_profile`은 단일 행이라 컬럼을 늘리면 종류가 늘 때마다 스키마가 바뀌므로 쓰지 않는다.

*화면 — 새 페이지를 만들지 않는다.* ③ 발송 단계와 메일 작성 화면에 **[문구 편집] 모달**을 둔다. 보내는 자리에서 고치는 것이 더 편하고, `/company`가 `requireRole(['admin'])`이라 매니저가 못 들어가는 문제도 우회된다. 권한은 액션에 `message_template_manage: ['manager','admin']`(신규 키).

*치환* `{회사명} {대표자} {회사전화}` ← `getCompanyProfile()`, `{고객명} {연도} {차수} {점검일}`, `{작성자}`. **상호가 `company_profile` 한 곳으로 수렴한다 — 최대 실익이다.** *폴백*: 행이 없으면 코드의 현행 문구. *미리보기*: 실제 값이 채워진 결과를 나란히, 치환되지 않은 `{…}`는 경고. *이력*: 발송 시 **렌더된 본문**을 `report_deliveries.body`에 저장 — 지금은 제목만 남아(`:165-169`) 문구가 가변이 되면 "그때 무엇을 보냈는지"가 복원 불가가 된다. 관계인 보고는 ③의 완료 증빙이다.

**D-2 ④에 별지 4호 조회(4-4)** — `GENERATED_DOC_KINDS.report4`가 이미 있다(`doc-requirements.ts:96`). ④ 문서 목록에 4·9·10호를 함께 놓는다.

**D-3 알림 자동 소멸(4-7)** — `notifications`의 `reference_id`·`reference_type`(`lib/notify.ts:16-22`)으로 단계 완료 시 그 점검의 **미읽음 기한 알림을 읽음 처리**한다. **삭제하지 않는다**(지우면 "언제 알렸는지"를 잃는다). 참고: `timeline-actions.ts:181` 주석이 `recordSubmissionAction`을 "알림 소멸 조건"이라 하지만 실제 함수(`:182-197`)는 컬럼 갱신과 로그만 한다 — **주석은 의도이고 구현이 아니다.**

### 왜 초안보다 줄었나 (2026-08-12 재검토)

| 항목 | 초안 | 확정 | 이유 |
|---|---|---|---|
| 마이그레이션 | 2개(128 `completed_source`·129) | **1개** | 근거 없는 완료를 없애 구분 컬럼이 불필요 |

핵심은 하나다. **근거 없는 완료를 허용하니까** → 자동이 그걸 지울까 봐 → 구분 컬럼이 필요하고 → 예외 규칙이 필요했다. 근거를 남기게 하면 사슬이 통째로 사라지고, 부수적으로 **③을 어떤 방법으로 보고했는지가 기록에 남아 증빙이 좋아진다.**

## #5 사이드바 정리 — 대분류를 늘리지 않고 구분선으로

상태: **기안 완료, 구현 전** · A안 확정(2026-08-12)

요구: *"점검현황모니터링, 점검대장, 점검표관리, 보고서(대분류) 안으로 넣어서 관리하는 것 어때 검토해줘"*

### 조사 — 보고서 대분류는 일주일 전에 해체했다

`sidebar.tsx:69-70`에 그 자리가 주석으로 남아 있다:
> *'보고서' 메뉴 소멸 (소방계획서_8 Phase B H-6d·D-8) — 고객별 문서·별지는 고객관리>소방계획서 트리, 제출 현황은 대시보드 위젯, 연차·일괄 생성은 점검확정>배치 발행. `/reports`는 새 위치로 리다이렉트.*

소방계획서_8 **D-8 "보고서 센터 해체"**(2026-08-04 결정, Phase B 2026-08-05 푸시 완결)가 없앤 것이다. 해체 이유(§2-4): *"보고서 센터의 애매한 위치 — 고객별 문서 현황·별지 생성이 트리와 중복되는 별도 화면. **입력 지점이 둘로 늘어** 유지·혼동 비용."*

**즉 "여러 기능을 한 대분류에 모아 둔 것"이 문제였고, 풀어서 각자의 업무 맥락으로 보낸 것이 D-8이다.** 다시 모으면 "문서를 어디서 만드나"가 또 둘이 된다.

### 그러나 문제의식은 정확하다

소방안전관리 그룹이 **11개로 가장 길고 성격이 섞여** 있다. 그리고 `sidebar.tsx:60` 주석이 이미 분류를 적어 뒀다 — *"일상 점검 흐름순 → 정산(매니저↑) → 마스터데이터(점검표·지역배정)는 맨 아래"*. **분류는 이미 있는데 화면에 드러나지 않은 상태**다.

### 지목된 셋은 서로 다른 종류다

| 항목 | 실체 | 성격 |
|---|---|---|
| 점검현황 모니터링 (`/inspection-plans/monitor`) | 기한 임박(D-3) 건수 배지가 사이드바에 붙는다(`:192`) | **행동 유도** |
| 점검 대장 (`/inspection-ledger`) | *"연간 점검 실적·계약 대장"*(`page.tsx:7-8`), `customers` 전체를 읽음(`:16-19`) | **명부 조회** |
| 점검표 관리 (`/inspection-sheets`) | 점검표 **양식** 등록·수정 | **마스터데이터** |

셋의 공통점은 "자주 안 쓴다"뿐인데 **빈도는 분류 기준이 아니다.** 한 이름으로 묶으면 "모니터링을 왜 보고서에서 찾지?"가 된다.

### 결정 (2026-08-12 사용자 확정)

- **D-1 A안 채택** — **새 대분류를 만들지 않고** 소방안전관리 그룹 안에 구분선을 넣어, 주석에만 있던 분류를 화면에 드러낸다. **보고서 대분류 재생성은 하지 않는다**(D-8 번복 금지).
- **D-2 점검 대장은 고객 관리의 탭으로 흡수** — `customers`를 통째로 읽는 뷰라 고객 관리와 원천이 같다. 메뉴 항목이 하나 준다.

### 설계

```
소방안전관리
  고객 관리 · 점검확정 · 점검 달력 · 점검 업무
  ── 현황 ──   점검현황 모니터링
  ── 정산 ──   정산현황 · 세금계산서 발행        (매니저↑)

- `NavItem`에 **`divider?: string` 한 필드만 추가**하고 `sidebar.tsx` 렌더에서 항목 앞에 소제목 줄을 그린다. **클릭 깊이 불변(2단 유지), 대분류 수 불변.**
- 헤더 브레드크럼(`header-title.tsx`)이 `NAV_GROUPS`를 경로→메뉴명 매칭에 재사용하므로(`:35` 주석), **구분선이 매칭을 깨뜨리지 않는지 확인**한다.

- **문의요청**은 점검 흐름 한가운데(`:71`) 끼어 있어 자리가 어색하다 — 접수 업무이므로 맨 아래로 내리되 구분선은 붙이지 않는다.
