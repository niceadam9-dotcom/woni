## 1. 발단

2. **주변 현황**은 무엇을 입력하는 칸인가
3. **관할 소방서**는 자동완성이 안 되는가

## 2. 현행 진단

### 2-1. 위치도는 실제로 두 곳이고, 문서에 2장 삽입된다 (Q1)

| 구분 | 1.3 위치도 | [지도·사진] 위치도·약도 |
|---|---|---|
| 저장 | `sections.location.mapImage` (plan-assets) | `map_location` 슬롯 자산 (`{customerId}/assets/`) |
| 화면 | `plan-form13.tsx:136` ImageSlot | `customer-assets-client.tsx` 슬롯 카드 |
| 입력 수단 | **수동 업로드만** | 업로드 + **붙여넣기** + **주소 기반 자동 생성**(네이버 정적지도) |
| 문서 수집 | `fire-plan-generate.ts:261` → `kind:'map'` | `fire-plan-generate.ts:257` → `kind:'map'` |

둘 다 `kind:'map'`으로 수집돼 템플릿의 위치도 블록(`fire-plan-template.ts:410-411`)에 **나란히 2장 인쇄된다.** 저장소·화면만 다를 뿐 같은 용도이고, 기능은 슬롯 자산 쪽이 **상위 호환**(자동 생성·붙여넣기 보유).

> 이 건은 `소방계획서_9.md §5-4`에 이미 발견·기록(image-42)돼 있었으나 v2 보류로 미착수 상태였다.

**피난 쪽도 같은 구조의 중복이 있다**: 슬롯 `evac_*`(kind `evacuation`) + `evacPlan.mapImage`(kind `evacuation`) + `evacMaps[].image`(kind `evacmap`) — 최대 3중.

### 2-2. 주변 현황 = 서식 1.3 표의 자유 서술 한 칸 (Q2)

`fire-plan-template.ts:405` — `<th>주변 현황</th><td colspan="5">{loc.surroundings}</td>`.
서식에 별도 지침이 없는 **자유 서술**이며, 소방차 진입·연소 확대 판단에 쓰이는 맥락이다. 현재 placeholder는 `인접 건물·도로 등 주변 현황` 한 줄뿐이라 무엇을 어느 수준으로 적을지 알기 어렵다.

### 2-3. 관할 소방서는 **이미 자동 매핑되어 있다** — 화면이 안 보여줄 뿐 (Q3)

- 주소 확정 시 `quickAddressApplyAction`이 `region_fire_stations`에서 관할서를 찾아 `customers.fire_station`에 저장한다(`actions.ts:1500-1523`). 단 **고객 값이 비어 있을 때만** 채운다(`:1505`).
- 템플릿은 `loc.fireStation`이 비어 있으면 **고객 값으로 대체**한다(`fire-plan-template.ts:240`). 즉 **1.3 칸을 비워두면 자동값이 인쇄된다.**
- 그런데 1.3 화면(`plan-form13.tsx:146`)은 자동값을 표시하지 않는 **빈 입력칸**이라, 사용자에게는 "자동완성이 안 된다"로 보인다.
- **거리·도착예상도 동일 구조**(`template:241-242`) — `d.stationDistance`·`d.stationEta` 폴백이 있으나 화면에 안 보인다.

### 2-4. 진입 경로도는 자동 생성이 없다 — 기술적 제약도 있다 (Q4)

`fa.routeImage`는 수동 업로드 전용(`plan-form13.tsx:172`). 반면 위치도·표지는 네이버 정적지도로 자동 생성 중(`asset-actions.ts:85-101`, 지오코딩 → static map).

다만 **진입 "경로"는 정적지도만으로 그릴 수 없다.** 경로선을 그리려면 출발지(관할 소방서 좌표)와 경로 탐색 API(NCP Directions 등)가 필요하고, 현재 연동돼 있지 않다. 또 실무의 진입 경로도는 보통 **정문·진입 지점·장애물을 사람이 표시**한 것이라 완전 자동은 목적에 맞지 않는다.

### 2-5. 삽입 사진 종류가 [지도·사진] 슬롯과 정면으로 겹친다 (Q5)

`plan-form13.tsx:87-92`의 종류 선택지와 슬롯 자산의 대응:

| 삽입 사진 종류 | 겹치는 슬롯 |
|---|---|
| 건물 전경 (`building`) | `cover` 표지 건물 사진 |
| 위치도(지도) (`map`) | `map_location` |
| 피난경로도 (`evacuation`) | `evac_*` |
| 기타 (`etc`) | — (고유) |

즉 **4개 중 3개가 중복 입력 경로**다. 사용자가 여기서 위치도를 또 올리면 2-1의 2장에 더해 **3장까지** 삽입될 수 있다.

## 8-2. "메인 도로명"의 정의 — 3단계로 층을 나눈다

'메인 도로'는 두 가지 의미가 섞여 있어 단계를 분리한다.

| 단계 | 정의 | 데이터원 | 추가 비용 | 정확도 |
|---|---|---|---|---|
| **L1 접도 도로** | 건물의 **도로명주소가 가리키는 도로** = 건물이 접한 도로 | `address` 문자열 정규식 파싱 | **0원** | 높음(주소가 정확하면 100%) |
| **L2 정규 도로명** | 지오코딩 응답의 구조화된 도로명 필드 | NCP Geocode `addressElements`(`ROAD_NAME`) | 지오코딩 1회(기존 무료 한도 내) | 매우 높음 |
| **L3 간선 도로** | **소방차가 실제로 타고 오는 상위 도로** — 접도 도로가 `○○길`(이면도로)이면 그 위의 `○○로`·`○○대로` | Directions 5 응답의 `section[].name` 마지막 구간 | §9 연동 필요 | 실주행 기준 |

**핵심**: 주소 도로가 `길`로 끝나면 L1만으로는 "메인 도로"가 아니다. 이 경우에만 L3(§9)로 승격한다 — 즉 **A는 B 없이도 단독 도입 가능**하고, B가 들어오면 자동으로 정확해진다.

## 8-3. 도로명 파싱 규칙 (K-8)

한국 도로명주소 체계는 도로명이 **`대로`·`로`·`길` 세 접미사로만** 끝나고, 그 뒤에 건물번호가 온다. 이 구조를 그대로 쓴다.

```
// lib/address-parser.ts 추가
const ROAD_RE = /([가-힣A-Za-z0-9]+(?:대로|로|길))\s*(\d+(?:-\d+)?)(?:\s|$|,)/
// "경기 양평군 양평읍 마유산로 123-4" → road='마유산로', bldNo='123-4'

export function extractRoadName(address: string): {
  road: string          // '마유산로'
  tier: 'daero'|'ro'|'gil'   // 대로 > 로 > 길 위계
  bldNo: string
} | null
```

- **위계 판정**: `대로`=간선, `로`=주요, `길`=이면도로. `tier==='gil'`이면 UI에 "이면도로 — 간선도로는 §9 경로 조회로 확인" 힌트.
- **주의(오탐 방지)**: `~로` 앞에 지역명이 붙는 경우(`양평읍 도로`)와 구분하려면 **건물번호가 뒤따르는지**를 필수 조건으로 둔다(위 정규식이 이미 강제). 지번주소(`address_jibun`)에는 도로명이 없으므로 **파싱 대상에서 제외**.
- **폴백**: L1 실패 시 L2(지오코딩) 자동 시도 → 그것도 실패면 버튼에 "주소로 도로명을 찾지 못했습니다" 표시(입력칸은 그대로 수기 사용).

## 8-4. 생성 문장 — "채워주는 문장"이 아니라 "빈칸 있는 초안"

서식 1.3 주변 현황은 **소방차 진입 가부·연소 확대 판단 근거**다(`fire-plan-template.ts:405`). 자동으로 단정할 수 있는 것은 **접도 도로명뿐**이고 차로수·인접 건물은 현장 정보다. 그러므로 **전부 채우지 않고 뼈대만 제안**한다.

```
[북]측 마유산로에 접함(왕복 __차로).
동측 ____, 서측 ____, 남측 ____ 인접.
```

- **방위**는 자동 판정이 어렵다(건물 폴리곤 대비 도로 위치 필요) → **방위 칩 [북][동][남][서] 1클릭**으로 사람이 지정. 기본값은 미선택 `[ ]`.
- **차로수·인접 건물**은 `__` 빈칸으로 남긴다. 도로 폭·차로수를 주는 공개 API가 현재 연동돼 있지 않다(도로명주소 API는 도로 제원 미제공).
- L3(§9)가 있으면 한 줄이 추가된다: `소방차는 국도6호선(양평대로)에서 마유산로로 진입.`

## 9-2. 선행 블로커 — 출발지 좌표가 없다 (K-11)

경로 조회에는 출발지(소방서)와 목적지(건물) **좌표 2개**가 필요한데, 현재 소방서는 **이름 문자열뿐**이다.

```sql
-- 065_region_fire_stations.sql:4-9 — 좌표·주소 컬럼 없음
CREATE TABLE region_fire_stations (
  region TEXT PRIMARY KEY, fire_station TEXT NOT NULL, region_si TEXT, note TEXT);
```

지오코딩에 `"양평소방서"`를 넣는 방식은 **쓰지 않는다** — NCP Geocode는 주소 전용이라 POI명은 실패하거나 엉뚱한 좌표를 준다.

**제안: 마이그레이션 신규 1건으로 컬럼 3개 추가 + 22행 수기 시드**

```sql
ALTER TABLE region_fire_stations
  ADD COLUMN station_address TEXT,   -- 소방서 도로명주소
  ADD COLUMN station_lat  NUMERIC,   -- 위도 (지오코딩 1회 결과 고정 저장)
  ADD COLUMN station_lng  NUMERIC;
```

- 대상은 **22개 행뿐**(양평소방서 등, `065:16-40`) → 주소만 수기로 채우고 **시드 스크립트가 지오코딩해 좌표 확정**. 이후 런타임 지오코딩 불필요
- 소방서는 이전이 드물어 **정적 데이터로 두는 게 옳다**

> ✅ **결정(2026-08-07, 사용자): 출발지 = 관할 소방서(본서)**. 119안전센터 기준은 채택하지 않는다.
> 근거 3가지 — ① 서식 1.3의 항목명 자체가 **"관할 소방서 / 거리 / 도착예상"**이라 기재 기준이 관할서다. ② ERP는 이미 `region_fire_stations`로 관할서를 매핑해 `customers.fire_station`에 저장하고 있어(`actions.ts:1500-1523`) **데이터 단일 원천이 유지**된다 — 안전센터를 쓰면 매핑 테이블을 새로 만들고 행 수도 크게 늘어난다. ③ 화면에 표시되는 관할서와 계산에 쓰인 출발지가 **일치**해야 사용자가 값을 검증할 수 있다(다르면 "왜 이 거리인가"를 설명할 수 없다).
> 대신 도착예상은 **참고값**임을 화면·문서에 명시한다(9-7 ②).

## 9-5. 경로도 렌더 — Static Map은 선을 못 그린다 (K-13)

NCP Static Map v2는 `markers`는 지원하지만 **경로선(polyline) 파라미터가 없다**(현행 사용: `asset-actions.ts:94-101`). 따라서 **배경 지도 + 경로선 오버레이를 서버에서 합성**한다.

```
① path[] bbox 계산 → 중심 좌표·적정 level 산출
② Static Map으로 배경 PNG (기존 코드 재사용, w/h 800×600 scale 2)
③ 각 경로 좌표를 Web Mercator로 픽셀 변환
     px = (lng - centerLng) * (256*2^level / 360) + w/2
     py = 메르카토르 y 투영 후 동일 스케일 적용
④ SVG 오버레이 생성 — 경로 polyline(적색 4px, 흰색 6px 테두리)
     + 🚒 출발 마커 + 🏢 도착 마커 + "2.4km · 6분" 라벨
⑤ sharp.composite()로 PNG 합성 → 슬롯 저장
```

- **`sharp`는 이미 `node_modules`에 존재**(Next 의존으로 설치됨) — 직접 쓰려면 `package.json`에 **명시적 의존성으로 승격**해야 한다(Docker 프로덕션 빌드 안정성). 이것이 이 안의 유일한 신규 의존성
- **폴백**: sharp 도입을 피하려면 이미 운영 중인 **Gotenberg 8**(`docker-compose.prod.yml:21-23`)로 `배경img + SVG` HTML을 렌더 — 단 현재 사용 중인 라우트는 `/forms/chromium/convert/html`(PDF)뿐(`lib/pdf.ts:74`)이라 **스크린샷 라우트 가용 여부는 실측 확인 필요**

## 13-B. 레거시 사진 — "1장만 인쇄" (제안)

### 왜 지금 2장인가

`fire-plan-generate.ts`의 `refs[]`는 **출처별로 그냥 쌓기만** 한다. 슬롯 `cover`/`map_location`/`evac_*` → 서식 입력 → `photos[]` 순으로 push하고, 템플릿은 `kind`별로 모아 인쇄한다. 그래서 같은 용도의 이미지가 두 출처에 있으면 그대로 2장이 된다. D-1(K-2)은 `location.mapImage` 한 건만 막았다.

### 제안 — 생성 시 "단장(單張) kind" 규칙 (권고)

```
SINGLE_KINDS = { cover, map }      // 표지·위치도 = 문서에 1장
MULTI_KINDS  = { evacmap, route, etc, evacuation }   // 층별·기타 = 복수 허용
```

`collectImages` 직전에 **우선순위 dedupe** 1단계를 넣는다.

| 우선순위 | 출처 | 이유 |
|---|---|---|
| 1 | 슬롯 자산 (`cover`·`map_location`) | 자동 생성·붙여넣기를 가진 단일 원천(D-1 결정) |
| 2 | 서식 입력 (`location.mapImage`) | 레거시 폴백 |
| 3 | `photos[]`의 `building`·`map` 종류 | 가장 오래된 입력 경로 |

- 구현은 `refs` 배열에 `priority` 필드를 달고 `kind`가 `SINGLE_KINDS`면 최소 priority 1건만 남기는 **10줄 남짓**이다. K-2의 `hasMapSlot` 특수 처리는 이 규칙에 흡수돼 사라진다
- **`building` kind 주의**: 현재 표지 슬롯은 `cover`, 삽입 사진의 건물 전경은 `building`으로 **kind가 다르다**. 템플릿에서 쓰이는 위치가 다르면 dedupe 대상이 아니다 — 구현 전에 `fire-plan-template.ts`에서 `building`이 실제로 어디에 인쇄되는지 확인이 선행돼야 한다(미확인)
- **의도적 2장을 원하면**: 종류를 `기타`로 바꾸면 그대로 복수 인쇄된다(도피로 확보)

> 규모: 소(dedupe 10줄) + 확인 1건(`building` 인쇄 위치). 화면 경고(D-5)는 그대로 두되 문구를 "1장만 인쇄됩니다"로 바꾼다.

```sql
('분당','분당소방서','성남시')   -- 065:32
```

**성남시 주소면 `estimate`가 "성남소방서"를 만드는데, 분당 지역의 관할은 분당소방서다.** 성남소방서도 실재하므로 **틀린 값이 그럴듯하게** 들어간다 — 가장 나쁜 실패 방식이다.

### 제안 (C안)

| # | 내용 | 규모 |
|---|---|---|
| **C-1 (권고)** | **`estimate` 값에 확인 배지** — `⚠ 추정: 성남소방서 (확인 필요)`를 1.1·1.3에 표시. `resolveFireStation`은 이미 `source`를 반환하므로 **전달만 하면 된다** | 소 |
| **C-2** | **공공데이터로 시드 확장** — [경기도 소방서현황 및 관할구역](https://data.gg.go.kr/portal/data/service/selectServicePage.do?infId=DY1064185ZS30XUR8ZC912502184&infSeq=1) / [소방청 119안전센터 현황](https://www.data.go.kr/data/15065056/fileData.do)으로 `region_fire_stations`를 전국(또는 경기 전역) 확장 → **`estimate` 단계를 제거**할 수 있다 | 중 |
| C-3 | `estimate`를 **저장하지 않고 제안만** | — | 사용자 지시("비어 있지 않도록")와 충돌하므로 **미권고** |

> 현재 고객은 대부분 양평군 관내라 `estimate`가 실제로 발동할 일이 드물다. **C-1만 먼저** 하고 C-2는 관외 고객이 늘 때 하는 것을 권한다.
