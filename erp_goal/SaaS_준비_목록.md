# SaaS 출시 준비 목록 — 제품 밖에서 갖춰야 할 것들

> 작성 2026-10-01 · 짝 문서 `SaaS_전환_로드맵.md`(제품·코드 쪽) · 이 문서는 **홈페이지·법무·사업·영업·지원** 등 코드 밖 준비물.
> 대상: 소방점검 대행업체에게 소방안전관리 SaaS를 파는 1인 운영사(승진소방 → 운영사 분리 여부는 §4 결정).

## 0. 결론부터 — 홈페이지는 필요하다

필요하다. 다만 「회사 소개 홈페이지」가 아니라 **제품 랜딩 사이트**다. 이유 셋:
1. **법적 게시 의무** — 이용약관·개인정보 처리방침·사업자 정보(상호·대표·사업자번호·통신판매업 신고번호·주소·연락처)는 서비스 **밖에서도** 누구나 볼 수 있는 자리에 있어야 한다(전자상거래법·개인정보보호법). 로그인 뒤 앱 안에만 두면 안 된다.
2. **영업 입구** — 소방점검 대행업체 대표가 검색·소개로 들어와 「이게 뭔지·얼마인지·어떻게 시작하는지」를 5분 안에 알고 **데모 신청/문의**를 남길 자리. 지금은 `sjfire.co.kr/login`뿐이라 들어올 문이 없다.
3. **신뢰** — 요금·보안·회사 정보가 공개돼 있어야 결제 전환이 된다. PG(토스페이먼츠 등) 심사도 이 페이지들을 본다.

앱과 사이트는 **분리**한다 — 사이트는 정적(Next.js 정적 export·Astro·노션 퍼블리싱 등 아무거나), 앱 배포와 무관하게 바꿀 수 있어야 한다. 주소는 **지금은 `sjfire.co.kr`을 쓰고 나중에 제품 도메인으로 분리**한다(사용자 결정 2026-10-04, 배치는 §1 끝).

### 도메인 — 지금은 `sjfire.co.kr`, 나중에 분리 (사용자 결정 2026-10-04)

**고정 제약: 앱은 `sjfire.co.kr` 루트에서 옮기지 않는다.** 현장에 붙인 QR 라벨(`/t/{code}` — 개체·지점·건물·자체점검기록표)과 관계인에게 보낸 링크(`/p/{token}`)는 발급 때의 요청 호스트로 주소를 만든다(`lib/share-links.ts` `siteOrigin`). 즉 이미 인쇄된 라벨이 전부 `https://sjfire.co.kr/t/…`를 가리킨다. 앱을 `app.` 등으로 옮기면 벽에 붙은 라벨이 깨진다 — 옮기더라도 `/t/`·`/p/`는 영구 리디렉트로 살려야 한다. 모바일 앱도 서버 주소를 `extra.erpUrl=https://sjfire.co.kr`로 들고 있다(설치된 앱은 스토어 갱신 전까지 그 주소만 부른다).

**1단계 — 지금(제품명·도메인 정하기 전): `www.sjfire.co.kr` = 제품 사이트**

| 주소 | 용도 | 바꿀 것 |
|---|---|---|
| `sjfire.co.kr` | 앱(현행 그대로) — 로그인·`/t/`·`/p/` | 비로그인으로 `/`에 오면 로그인 대신 `www.`로 보낸다(로그인 화면 아래에 약관·처리방침·사업자 정보 링크) |
| `www.sjfire.co.kr` | 제품 사이트(정적) — 홈·기능·요금·문의·약관·처리방침·사업자 정보 | 지금은 `sjfire.co.kr`로 301 리디렉트 중(`erp/deploy/Caddyfile`) → Caddy `file_server`로 정적 폴더 서빙. 앱 컨테이너·배포와 무관 |
| `staging.sjfire.co.kr` | 스테이징(현행, noindex) | 없음 |

- 사이트 파일은 서버의 별도 폴더(예: `/srv/site`)에 두고 Caddy가 직접 서빙 — 사이트 수정이 앱 배포 회차를 타지 않는다.
- 사이트 문구는 처음부터 **「승진소방」을 제품명처럼 쓰지 않는다**(나중에 분리할 때 고칠 곳을 줄인다). 운영 주체·사업자 정보는 푸터 한 곳에만.
- 데모 신청 폼은 앱 API(`sjfire.co.kr/api/…`) 하나로 받아 메일/문자 알림(새 크론 없음).

**2단계 — 분리(제품명·상표 출원 뒤, Stage 3 전): 제품 도메인으로**

| 주소 | 용도 |
|---|---|
| `제품.co.kr`(+`.com`) | 제품 사이트 — `www.sjfire.co.kr`의 정적 폴더를 그대로 옮긴다 |
| `app.제품.co.kr` | 테넌트 앱(같은 앱·같은 배포, 호스트만 추가). 새 테넌트의 QR·링크는 이 주소로 발급 |
| `status.`·`help.` | 상태 페이지·도움말 |
| `sjfire.co.kr` | **승진소방(테넌트 #1)의 앱 주소로 영구 유지** — 이미 인쇄된 라벨이 살아 있어야 한다 |
| `www.sjfire.co.kr` | 제품 도메인으로 301 (또는 승진소방 회사 소개로 되돌림) |

분리하는 이유는 종전 그대로다 — `sjfire.co.kr`은 승진소방 회사 도메인이라 다른 업체(경쟁사)가 주소창에서 그 이름을 보면 안 쓴다. 그래서 **유료 테넌트를 받기 전**에는 2단계를 마친다.
⚠ 2단계에서 `siteOrigin`이 테넌트별 호스트를 고르게 해야 한다(지금은 요청 호스트 또는 `PUBLIC_SITE_URL` 하나) — Stage 1 테넌시 작업 목록에 넣는다.

## 4. 사업·회계·조직

| 항목 | 내용 |
|---|---|
| 운영 주체 | (a) 승진소방이 사업부로 운영 (b) 별도 사업자/법인. b가 영업·책임·투자에 깔끔하나 초기엔 a로 시작하고 테넌트 3곳 넘으면 b로 — 약관·계약 당사자가 바뀌니 **처음부터 b 전제로 문서를 쓰는 게 싸다** |
| 가격 책정 근거 | 원가: Supabase Pro·VPS·Gotenberg·Sentry·문자 단가(건당 ~20원)·AI 토큰·결제 수수료(~3%). 테넌트당 월 원가를 먼저 계산 |

| 창업 지원 | 벤처·초기창업패키지·클라우드 바우처(테넌트가 받을 수도) — 사업자 형태 확정 후 |
| 보험 | 사이버 배상책임보험(데이터 유출 시) — 테넌트 10곳 넘으면 검토 |
| 회계 | 구독 매출 인식(월 안분), 환불 처리, 미수 관리 |

## 5. 가격·플랜·결제

| 항목 | 내용 |
|---|---|
| 과금 축 | **대상물(건물) 수** 기준이 이 업종에 가장 직관적(대행업체 매출이 대상물 수에 비례). 좌석 수는 보조 상한. 예: Basic 대상물 50·사용자 3 / Standard 200·10 / Pro 무제한 |
| 부가 사용료 | 문자 건당(원가+마진), AI 분류 월 n회 포함 후 초과 과금, 저장 용량 |
| 무료 체험 | 30일·대상물 10개 제한·문자는 dry-run 또는 월 20건. 체험 만료 시 **읽기 전용**으로 두고 데이터는 보존(삭제는 90일 후 통지 뒤) |
| 결제 수단 | 국내 B2B SMB는 **계좌이체+세금계산서**가 기본, 카드 정기결제는 옵션. 초기엔 수동 청구(세금계산서 모듈)로 시작해도 된다 — PG 심사 대기 중에도 영업 가능 |
| 해지·환불 | 월 단위 해지, 선납 연간은 잔여분 환불 규정. 해지 후 데이터 반출 기간(30일)·삭제 시점 명시 |
| 할인 | 연간 선납 2개월 할인, 승진소방 네트워크 소개 할인 |

## 11. 운영 모델 — 「소방안전관리 SaaS」와 「승진소방 ERP」가 한 시스템에 있을 때 (2026-10-01 추가)

### 원칙: 코드 하나·배포 하나·**모듈 플래그**로 가른다. 포크하지 않는다.
승진소방은 **테넌트 #1이자 운영사**다. 같은 코드가 승진소방에게는 전 모듈(ERP 포함), 다른 테넌트에게는 소방안전관리만 보인다(`tenants.enabled_modules`). 저장소를 둘로 쪼개면 공통 기반(인증·사용자·알림·설정·모바일·문서 생성)을 두 번 고치게 되고, 1인 팀은 그걸 못 버틴다.

### 모듈을 3층으로 나눈다
| 층 | 모듈 | 누가 쓰나 | 변경 규칙 |
|---|---|---|---|
| **A. SaaS 핵심** | 고객·점검 달력·6단계 점검·점검표·별지 9/10/11호·소방계획서·문자·정산(후순위) | 전 테넌트 | 스테이징 **테넌트 #2 검증** 통과 + 릴리스 노트 + (법령 개정이면) 전 테넌트 동시 공지 후 배포 |
| **B. 공통 기반** | 로그인·사용자/역할·부서·알림·설정·회사 정보·모바일·PDF 생성·크론·`/ops` | 전 테넌트 + 운영사 | A와 같은 규칙. **B는 C를 import하면 안 된다**(의존 방향 게이트) |
| **C. 내부 ERP** | My Page·업무관리·영업·구매/재고·회계·게시판·전자결재·인사/휴가·회사 메일 | 승진소방만(`enabled_modules`에 없음) | 테넌트 #1에만 영향 → 가볍게 배포. 단 **B 테이블 스키마를 바꾸는 변경은 A 규칙** |

게이트(로드맵 Stage 1 정적 게이트에 추가): `src/app/(dashboard)/{customers,inspections,fire-plans,…}`(A)와 `src/lib`(B)가 C 디렉터리를 import하면 실패. C가 A·B를 import하는 건 허용. 이 한 줄이 「내부용 기능이 SaaS 핵심에 스며드는」 사고를 막는다.

### 승진소방을 「고객 #1」로 대우한다 (dogfooding)
- 승진소방 전용 편의(양평군 기본값·특정 담당자 기본 배정·회사 메일함)는 **테넌트 설정값**으로 내려야 한다. 코드에 승진소방이 남아 있으면 그게 곧 SaaS 결함이다(로드맵 Stage 2가 이 일).
- 승진소방이 요청한 기능은 먼저 「다른 대행업체도 쓰나?」를 묻는다 — 예면 A(전 테넌트), 아니면 C 또는 테넌트 설정. **A에 승진소방 특수 로직을 넣지 않는다.**
- 운영 계정 분리: 운영사 직원의 **`/ops` 권한(is_system)**과 **테넌트 #1 관리자 권한**은 다른 계정(또는 명시적 역할 전환+기록). 지원 목적으로 다른 테넌트 데이터를 볼 때는 접근 기록을 남긴다.

### 배포·릴리스 운영
| 항목 | 방식 |
|---|---|
| 브랜치 | 단일 `main`, 기능 플래그. 장기 브랜치·포크 금지 |
| 릴리스 주기 | A·B는 **주 1회 정기 창**(예 화요일 저녁), 긴급 수리는 수시. C는 수시 |
| 검증 | 스테이징에 **테넌트 #1 사본 + 테넌트 #2(샘플)** 둘을 늘 두고, A 변경은 둘 다 통과해야 운영 |
| 법령 개정 | `law-revision-check` 알림 → 점검표/서식 마스터 개정 → **전 테넌트 동시 반영**(이게 SaaS의 핵심 가치) → 앱 내 공지+메일. 테넌트 오버라이드가 있으면 충돌 목록을 운영사가 검토 |
| 운영 점검 | 무중단(Stage 4 전까지는 심야 창 고지) |
| 회차 기록 | 지금의 `_deployNN` 수기 → CI 릴리스 번호·릴리스 노트로 대체 |

### 지원·운영 루틴
| 주기 | 할 일 |
|---|---|
| 매일 | `/ops` 대시보드: 테넌트별 오류·크론 실패·문자 실패·PDF 실패. Sentry 알림 처리 |
| 매주 | 릴리스 창, 기능 요청 보드 정리, 체험 테넌트 전환 현황 |
| 매월 | 청구(세금계산서)·사용량 정산, 법령·서식 변경 확인, 백업 복구 점검 1회 |
| 분기 | 테넌트 리뷰(이탈 징후·요청), 키 로테이션, 가격·플랜 재검토 |
| 사고 시 | 72시간 통지 절차, 테넌트별 영향 범위 산정(격리 덕에 테넌트 단위로 말할 수 있어야 한다) |

### 상품 구조 — 기본 = 소방안전관리, 나머지 = 부가서비스(애드온) (사용자 확정 2026-10-01)
| 구분 | 모듈 | 판매 방식 | 조건 |
|---|---|---|---|
| **기본 상품** | 소방안전관리(A층 전부) | 플랜(대상물 수) | 출시 시 |
| **애드온 1순위** — 대행업체가 바로 쓸 만한 것 | 정산현황·세금계산서(점검비 청구) · 업무관리(일정·업무·차량 운행) · 영업(견적·거래처) | 모듈당 월정액 또는 상위 플랜 포함 | 테넌트 #2로 일반화 검증(승진소방 전용 로직 0) 통과 후 |
| **애드온 2순위** | 인사/휴가·전자결재·게시판 | 월정액 | 수요 확인 후 |
| **판매 안 함(내부 전용)** | 회사 메일(단일 Gmail)·회계(전표/손익/부가세 — 세무 책임 범위가 넓어 SaaS로 팔면 리스크) | — | 승진소방만 |

- 애드온도 **같은 플래그 하나**(`enabled_modules`)로 켠다. 과금은 `tenants.plan` + 애드온 목록, 청구는 월 세금계산서에 줄 추가.
- 애드온을 켜기 전 체크 3가지: ① 테이블에 `company_id`·RLS가 있는가(로드맵 Stage 1이 전 테이블에 깔아 두는 이유) ② 승진소방 특수값이 코드에 남았는가 ③ 도움말·약관 범위에 들어갔는가.
- 켜지 않은 모듈은 사이드바·라우트·크론 모두에서 **보이지 않아야** 한다(플래그 오프 = 403, 크론은 해당 테넌트 건너뜀).

### 데이터·과금 운영
- 공유 DB지만 C 모듈 테이블은 애드온을 켠 테넌트 것만 찬다. 백업·복구는 전체 단위, 내보내기/삭제는 테넌트 단위(Stage 4).
- 승진소방 테넌트는 `plan = internal`(과금 없음, 전 모듈 켜짐).

### 조직·역할 (1인 + AI 전제)
- 역할을 **시간으로** 나눈다: 오전 지원·운영, 오후 개발. 지원 채널 응답 기준은 약관과 맞춘다.
- 운영사 역할 분리 시점: 테넌트 3곳 이상이면 「운영사=별도 사업자」(§4) + 지원 담당 1명(파트타임이라도).
- 승진소방 현업(점검원·관리자)이 **첫 베타 테스터**: 매 릴리스 전 테넌트 #1 사본으로 하루 먼저 써 본다.

### 한 문장
「승진소방 ERP 안에 SaaS를 넣는」 게 아니라 **「SaaS 플랫폼 위에 승진소방이 테넌트 #1로, 내부 ERP는 그 테넌트만 켠 모듈로」** 올라타는 구조로 운영한다.
