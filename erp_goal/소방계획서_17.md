## 1. 현행 진단 — 지금은 "이력"이 아니라 "마지막 한 건"이다

개정이력 표는 성격이 다른 두 원천을 합쳐 그린다.

| 원천 | 성격 | 한계 |
|---|---|---|
| `fire_plans` 행 | 문서 생성·업로드 **실적**에서 자동 파생 | 서술이 `note` 자동 문구뿐, 사람이 고칠 수 없음 |
| `fire_plan_forms.sections.revision` | 사용자 입력(작성일·개정내용) | **슬롯이 1개** — 저장할 때마다 통째로 덮어씀 |

### K-1 ⚠ 과거 개정 사유가 남지 않는다 (핵심)
`saveFirePlanRevisionAction`이 `sections.revision`에 `{revisionDate, revisionNote}` **객체 하나를 덮어쓴다**(`fire-plan-form-actions.ts:40-43`, 저장은 `saveSection`의 키 단위 치환 `:22`). 작년에 적은 개정 사유는 올해 저장하는 순간 사라진다. 요구 #19의 "이력 나열"·"추가 서술"이 원천적으로 불가능한 이유.

### K-2 연도 개념이 없다
화면 표(`plan-tab-view.tsx:450-457`)는 전 연도 행을 `created_at` 순으로 일렬 나열한다. 연도 그룹·필터·연도별 건수가 없다.

### K-3 행 단위 추가·편집 수단이 없다
표는 `revisionRows`(= `fire_plans` 파생, `customers/[id]/page.tsx:575-577`) **읽기 전용**이다. 문서 생성 없이 일어난 변경(설비 교체로 1.4 수정 등)은 이력에 남길 방법이 없다.

### K-4 작성자·검토·승인이 항상 빈칸
인쇄 표는 6열(순번·일자·주요 개정내용·작성자·검토·승인)인데(`fire-plan-template.ts:347`), 과거 행 `author`는 조립 단계에서 **항상 `''`**(`fire-plan-generate.ts:141`), 검토·승인 열은 **모든 행이 빈 `<td>`**(`:348-350`). 소방계획서_15 감사의 M-13과 동일 건.

### K-5 ✅ 인쇄 표 순번 어긋남 — **수정 완료(선반영)**
현재 작성분은 `과거건수+1`로 찍는데 예약 빈 행은 항상 `2,3,…,8` 고정이었다(`fire-plan-template.ts:350`). 과거 행이 1건이라도 있으면 `3번 다음에 2번`이 오는 식으로 **생성 2회차부터 항상** 어긋났다.
→ 빈 행 시작값을 `(revisions.length)+i+2`로 바꿔 해소. 과거행 0·1·3건에서 순번 연속성 검증 완료.

## 2. 제안 — 개정이력을 독립 테이블로 승격

### 2-1. 마이그레이션 120 `fire_plan_revisions`

```sql
-- 120_fire_plan_revisions.sql
CREATE TABLE IF NOT EXISTS fire_plan_revisions (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id   UUID NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  year          INT  NOT NULL,              -- 연도별 그룹의 축 (K-2)
  seq           INT  NOT NULL,              -- 연도 내 순번
  revised_on    DATE,                       -- 개정일 (비우면 생성일)
  content       TEXT NOT NULL DEFAULT '',   -- 주요 개정내용 — 행마다 보존 (K-1)
  author_name   TEXT,                       -- 작성자 (K-4)
  reviewer_name TEXT,                       -- 검토
  approver_name TEXT,                       -- 승인
  source        TEXT NOT NULL DEFAULT 'manual'
                CHECK (source IN ('generated','uploaded','manual')),
  fire_plan_id  UUID REFERENCES fire_plans(id) ON DELETE SET NULL,  -- 생성 실적 연결
  created_by    UUID REFERENCES profiles(id) ON DELETE SET NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_fire_plan_revisions_seq
  ON fire_plan_revisions (customer_id, year, seq);
CREATE INDEX IF NOT EXISTS idx_fire_plan_revisions_cust
  ON fire_plan_revisions (customer_id, year DESC, seq);
ALTER TABLE fire_plan_revisions ENABLE ROW LEVEL SECURITY;
-- 접근은 서버 액션(createAdminClient)만 — 096·119 관례와 동일
```

관례 준거: `IF NOT EXISTS`·RLS enable·정책 없음(서버 액션 전용)·`ON DELETE SET NULL` — `096_fire_plan_forms.sql`·`119_plan_text_library.sql`과 동일.

### 2-2. 한 테이블이 세 요구를 동시에 푼다

| 요구 (#19) | 해결 |
|---|---|
| 년도별 이력 히스토리 | `year` 컬럼 + `(customer_id, year, seq)` 유니크 → 화면은 연도 그룹, 연도별 건수 표시 |
| 업데이트 건 나열 | 문서 생성·업로드 시 `source='generated'\|'uploaded'` 행 자동 append(현행 `fire_plans` 파생과 정보량 동일) + 사용자가 `source='manual'` 행 직접 추가 |
| 추가 서술 | `content`가 행마다 존재 → 덮어쓰기 소멸. `author/reviewer/approver`까지 실값으로 채워 K-4 동시 해소 |

### 2-3. 이관(백필) — 유실 0

1. 기존 `fire_plans` 전 행 → `source='generated'`(수동 업로드분은 `'uploaded'`) 행으로 1회 백필. `year`=행의 year, `seq`=연도 내 `created_at` 순, `revised_on`=`created_at::date`, `content`=`note ?? '{year}년 소방계획서{ (개정N)}'`(현행 자동 문구 규칙 그대로), `fire_plan_id`=원행 id.
2. `sections.revision`의 단일 슬롯 → **가장 최근 연도의 마지막 행**으로 이관(값이 있을 때만).
3. 조회는 새 테이블 우선, 행이 하나도 없으면 기존 경로로 폴백 — 백필 실패 시에도 화면이 비지 않는다.

`sections.revision`은 **쓰기 중단·읽기 폴백**으로만 남긴다(즉시 삭제하지 않음).

### 2-4. 인쇄 연동

- 조립(`fire-plan-generate.ts:137-142`)이 `fire_plans` 대신 `fire_plan_revisions`를 읽어 `revisions[]`를 만든다 — `author`를 `''`로 박던 자리에 `author_name`이 들어간다.
- 템플릿(`fire-plan-template.ts:347-350`)에 **검토·승인 열 값**을 넘긴다(현행 빈 `<td>` → `v(r.reviewer)`·`v(r.approver)`). 값이 없으면 지금처럼 빈칸이라 수기 서명 운용과도 호환.
- **화면=연도별 그룹, 인쇄=전 연도 시계열 통합**. 법정 서식의 개정이력은 그 문서 전체의 이력이므로 인쇄를 연도로 쪼개지 않는다.
- 현 작성분을 별도 행으로 덧붙이던 `:349`는 제거한다 — 이제 사용자 입력도 테이블의 한 행이라 이중 표기가 된다.

### 2-5. UI — 보관함 개정이력 카드 교체

`plan-tab-view.tsx`의 `sel === 'archive'` 블록(`:435-488`)을 연도 그룹 타임라인으로.

```
개정이력                                   [+ 개정 추가]
┌ 2026년 · 3건 ────────────────────────────────────┐
│ 3  2026-08-10  설비 교체로 1.4 수정      홍길동  [✏][🗑]  수동
│ 2  2026-05-02  2026년 소방계획서 (개정2) 홍길동  [✏]      생성
│ 1  2026-01-15  2026년 소방계획서 작성    홍길동  [✏]      생성
└──────────────────────────────────────────────────┘
┌ 2025년 · 1건 ──────────────────────── (접힘) ────┘
```

- 최신 연도만 펼치고 나머지는 접는다(연도 헤더에 건수).
- 행 편집은 인라인. `source='manual'` 행만 삭제 가능, 자동 행은 **일자·출처 잠금 + 서술/작성자/검토/승인만 편집**(이력의 사실성과 편집 자유를 동시에).
- 저장은 미저장 이동 확인창(unsaved-nav)과 동일 규약 — 폼 상태 변경 시 `dirty=true`.

### 2-6. 서버 액션 — `fire-plan-revision-actions.ts` 신설

전부 `requirePermission('customer_manage')` + `createAdminClient()` + `revalidatePath` (fire-plan-form-actions.ts 관례).

| 액션 | 시그니처 | 비고 |
|---|---|---|
| `listRevisionsAction` | `(customerId) → { years: {year, rows[]}[] }` | 연도 desc·seq desc |
| `addRevisionAction` | `(customerId, year, input) → { id }` | `seq`는 서버가 `max(seq)+1` 계산(클라이언트 신뢰 금지) |
| `updateRevisionAction` | `(id, input) → {}` | 자동 행은 `revised_on`·`source` 변경 거부 |
| `deleteRevisionAction` | `(id) → {}` | `source='manual'`만 허용 |
| `appendGeneratedRevisionAction` | `(customerId, year, firePlanId, note) → {}` | 생성·업로드 파이프라인에서 호출 |

`seq` 채번은 유니크 인덱스와 경합할 수 있다 — 동일 `(customer_id, year)`에 대해 `max(seq)+1` 후 삽입 실패(23505) 시 1회 재시도.

## 5. 리스크

- **백필 정확도**: `fire_plans`에 수동 업로드분과 자동 생성분이 섞여 있다(`pdf_path` 유무·`note` 문구로 구분). 오분류해도 `source` 라벨만 틀리고 이력 자체는 보존되므로 영향은 표시 수준.
- **연도 판정**: `fire_plans.year`는 계획서 연도이고 `created_at`은 실제 생성 시각이라 연말·연초에 어긋날 수 있다. 그룹 축은 **`year`**(계획서 연도)로 잡고, 표시 일자는 `revised_on`을 쓴다.
- **인쇄 회귀**: `:349`(현 작성분 별도 행) 제거 시 백필이 누락되면 마지막 개정이 사라져 보인다 — A-1 백필 검증을 A-3의 선행 조건으로 둔다.

## 6. 부수 제안 — #16 별지 서식 노드 위치

요구 원문: "별지 서식 회차별작성 조회를 보관함 개정이력 다음으로 내리던지 아니면 다른 좋은 방안".

현재 좌측 트리(`plan-tab-view.tsx:397-411`)는 `📑 별지 서식 > 회차별 작성·조회` → 구분선 → `🗂 보관함·개정이력` 순이다.

**단순 순서 교체는 권하지 않는다.** 별지 서식은 **회차마다 반복 사용하는 작업 화면**이고 보관함은 **완료물 조회**다. 사용 빈도가 높은 쪽을 아래로 내리면 클릭 동선이 나빠진다.

**권장안 — 성격으로 묶는다.** 트리를 `작성(1장~3장 + 별지 서식)` / `보관·이력(보관함·개정이력)` 두 그룹으로 나누고, 지금의 구분선을 그룹 라벨로 승격한다. 별지는 작성 그룹의 마지막에 그대로 두고, 보관함이 시각적으로 분리된 하단 블록이 된다. 순서는 그대로지만 "왜 이 순서인지"가 화면에 드러나 요구의 의도(별지가 보관함보다 위에 있어 헷갈림)를 해소한다.

대안: 별지를 1장~3장과 같은 레벨로 올려 `1장·2장·3장·별지`를 한 묶음으로 보이게 하는 것도 가능하다. 어느 쪽이든 **개정이력 개편(A-2)에서 보관함 노드를 손대므로 그때 함께 처리**하는 것이 비용이 낮다.

이 항목은 본 문서 범위 밖(별건)으로 두고, 위 권장안 채택 여부만 확정되면 A-2에 얹는다.

**후속 재확정(2026-08-11)**: 사용자가 구현된 그룹 라벨 화면을 확인한 뒤 **별지 서식을 보관·이력 아래(맨 아래)로 이동**하기로 재확정 — 위 권장안(순서 유지)은 폐기, 14.md #16 최종 처리. 좌측 트리·모바일 드롭다운(`NAV_ALL`) 모두 `본문 → 보관·이력 → 별지 서식` 순으로 교체(`plan-tab-view.tsx`).
