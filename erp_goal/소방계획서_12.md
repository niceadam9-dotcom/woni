## 1. 발단

1.4 화면에서 두 가지가 지적됐다.

1. **[저장] 버튼이 비활성**이다 — 왜 눌리지 않는지 화면이 설명하지 않는다
2. **저장이 느리다** — 클릭 후 버튼이 계속 비활성인 채로 대기가 길다

## 2. 현행 진단

### 2-1. 비활성은 의도된 설계다 (K-1)

`plan-form14.tsx:429`
```tsx
<button onClick={save} disabled={!dirty || isPending}>
```

2026-08-05 사용자 확정 규약 — "토글마다 자동 저장 폐지 → 최종 [저장] 1회 + 이탈 가드"(`plan-form14.tsx:97`). 따라서 **비활성 자체는 버그가 아니다.** 문제는 그 상태를 화면이 말해주지 않는다는 것이다. 푸터에는 `설치 N종 · 마지막 확인 MM-DD`만 있고(`plan-form14.tsx:418`) 미저장 여부 표시가 없다.

### 2-2. 한 화면에 저장 버튼이 2개다 (K-2) — 편의 문제의 본체

| 버튼 | 위치 | 저장 대상 | dirty 상태 |
|---|---|---|---|
| **[저장]** | 본문 푸터 `plan-form14.tsx:429` | 설비 체크 + 층별 수량 | `dirty` (`plan-form14.tsx:90`) |
| **[모두 저장]** | 설비 대장 패널 sticky `plan-form14-specs.tsx:651` | 세부 제원 | `dirtyCount` (`plan-form14-specs.tsx:108`) |

제원만 고치면 본문 [저장]은 계속 비활성이고, 반대도 마찬가지다. **이탈 가드는 이미 둘의 합집합**으로 통합돼 있는데(`plan-form14.tsx:112` `erp:plan-dirty` union) **저장 버튼만 분리돼 있다** — 자기 불일치다.

체크(√) 순간 패널이 자동으로 열리므로(`plan-form14.tsx:167-172`) 사용자는 자연스럽게 두 영역을 오가게 되고, 그만큼 "한쪽만 저장하고 이탈"이 쉽다.

### 2-3. 저장 액션이 순차 왕복 6회다 (K-3)

`facilities-actions.ts:11-51` `saveFacilitiesAction`:

```
requirePermission → auth.getUser()          (auth.ts:14-18, 요청 내 cache)
delete fire_facilities                       (:21)
insert fire_facilities                       (:28-31)
delete fire_facility_floors                  (:34)
insert fire_facility_floors                  (:38-41)
update buildings (확인일)                     (:44-47)
revalidatePath                               (:49)
```

전부 `await` 순차다. 설비 / 층별 / 확인일 세 갈래는 **서로 독립**이며, 같은 테이블 안에서만 delete→insert 순서 의존이 있다.

**실측**(`scripts/_probe-latency.mjs`, 스테이징, 5회 중앙값):

| 패턴 | 소요 |
|---|---|
| 단일 왕복 | **200ms** |
| 순차 4회 | **767ms** |
| 병렬 4회 (`Promise.all`) | **197ms** |

→ 현재 액션의 DB 구간만 **약 1.0초**, 인증 포함 **약 1.2초**.

### 2-4. `router.refresh()`가 고객 상세 페이지를 통째로 재실행한다 (K-4)

`plan-form14.tsx:195` (그리고 `:202` `verifyOnly`)
```ts
router.refresh()
```

대상 `customers/[id]/page.tsx`는 **825줄 · `.from(` 19회**다. 저장 결과는 이미 로컬 state와 동일한데도 전 서버 컴포넌트를 다시 돌린다. 화면에서 서버 값에만 의존하는 것은 푸터의 `b.verified_at` 하나뿐이다(`plan-form14.tsx:418`).

`revalidatePath`(`facilities-actions.ts:49`)가 이미 캐시를 무효화하므로 **다음 진입 시 최신은 보장**된다.

**체감 합계 ≈ 2초**, 그 구간 내내 `isPending`으로 버튼 비활성.

### 2-5. ⚠ delete-then-insert 데이터 유실 위험 (K-5)

`facilities-actions.ts:21-31`
```ts
await admin.from('fire_facilities').delete().eq('building_id', buildingId)  // 에러 미확인
if (facRows.length) {
  const { error } = await admin.from('fire_facilities').insert(facRows)
  if (error) return { error: `설비 저장 실패: ${error.message}` }           // 이미 지워진 뒤
}
```

- `delete`의 error를 **확인하지 않는다**
- 트랜잭션이 아니다 → **delete 성공 + insert 실패 = 기존 설비 데이터 전부 소실, 복구 불가**
- `fire_facility_floors`(`:34-41`)도 동일 구조

발생 확률은 낮으나 손실이 비가역이다. 근본 해법은 S3(단일 RPC·트랜잭션)이나 이번 범위에서 미채택 → **§5 잔여 리스크로 명시 보존**한다.

### 2-6. 비고 (K-6)

`verifyFacilitiesAction`(`facilities-actions.ts:54-66`)도 `router.refresh()` 경로를 쓴다(`plan-form14.tsx:202`). S1을 적용하면 이쪽도 같은 방식으로 정리해야 일관된다.

## 3. 설계

### S1 — `router.refresh()` 제거, 확인일만 응답으로 받는다

- `saveFacilitiesAction` / `verifyFacilitiesAction` 반환형에 `verifiedAt: string` 추가
- 클라이언트는 `const [verifiedAt, setVerifiedAt] = useState<string | null>(null)` 을 두고 푸터를 `verifiedAt ?? b.verified_at` 로 표시
- `switchBuilding`(`plan-form14.tsx:135-144`)에서 `setVerifiedAt(null)` 리셋 — 건물 전환 시 이전 건물의 확인일이 남으면 안 된다
- `router.refresh()` 2곳 삭제. `useRouter` 미사용이 되면 import도 제거
- `revalidatePath`는 **유지** — 다음 진입·다른 화면의 최신성 보장

기대 효과: **약 1초 단축**

### S2 — 서버 액션 병렬화

세 갈래를 `Promise.all`로 묶는다. 같은 테이블 내 delete→insert 순서는 각 갈래 안에서 유지한다.

```
├ 설비  : delete → insert
├ 층별  : delete → insert     ← 세 갈래를 Promise.all
└ 확인일: update
```

- 각 갈래는 error를 문자열로 반환하고, 호출부가 모아서 첫 에러를 표면화
- **`delete`의 error도 확인**한다(K-5 완화 — 근본 해결은 아니다)

기대 효과: 6회 순차(~1.2초) → **2회 왕복 분(~400ms)**

### U1 — 미저장 상태를 화면이 말하게

푸터 [저장] 옆에 배지:

- 미저장 있음 → `● 미저장` (본문/제원 내역을 구분해 표기, 예: `● 미저장 · 제원 3섹션`)
- 미저장 없음 → `변경 없음`

이를 위해 `PlanForm14Specs`의 통지를 **boolean → 개수**로 넓힌다:
`plan-form14-specs.tsx:111` `onDirtyChange?.(dirtyCount > 0)` → `onDirtyChange?.(dirtyCount)`
(호출부는 `plan-form14.tsx:460` 한 곳뿐)

### U2 — `Ctrl/⌘+S` 단축키

`keydown` 리스너에서 `preventDefault()` 후 저장 실행. 저장할 것이 없으면 무동작. 표는 길어서 푸터까지 스크롤해야 하는 비용을 없앤다.

### U3 — 저장 버튼 통합 (편의 효과 최대)

- 활성 조건: `!(dirty || specsDirty) || isPending`
- 클릭 시 **본문(설비·층별) + 제원을 한 번에** 저장. 두 액션은 서로 독립이므로 `Promise.all`로 동시 실행
- dirty가 아닌 쪽은 **호출하지 않는다**(불필요한 쓰기 금지)
- 자식의 `saveAll`(`plan-form14-specs.tsx:290`)은 현재 `void` 반환이라 await 불가 → **결과를 반환하는 async 함수로 분리**하고, 부모에 등록(`onRegisterSaveAll`)해 부모가 await 할 수 있게 한다. 패널 자체의 sticky [모두 저장]은 **유지**(패널만 보고 있을 때의 경로)
- 메시지는 두 결과를 합쳐 1줄로

## 4. 미채택 / 보류

| 항목 | 내용 | 사유 |
|---|---|---|
| **S3** | 단일 RPC(Postgres 함수)로 delete+insert+update를 트랜잭션 처리 | 왕복 1회 + K-5 근본 해결이지만 마이그레이션 동반. 이번 범위 밖 — **재검토 대상으로 보존** |
| **U4** | 낙관적 UI(클릭 즉시 성공 표시, 실패 시 롤백) | S1+S2로 0.6초가 되면 필요성이 낮고 실패 처리 복잡도가 큼 |
| **U5** | sticky 저장 바 | U1+U2로 대체 가능 |

## 5. 잔여 리스크

- **K-5(데이터 유실)는 이번 범위로 해결되지 않는다.** S2에서 delete 에러 확인을 추가해도 "delete 성공 → insert 실패" 창은 남는다. S3 채택 전까지 유효한 리스크로 유지한다.
- U3로 저장 경로가 두 컴포넌트에 걸치므로, **한쪽 실패 시 다른 쪽만 저장되는 부분 성공**이 생긴다. 실패한 쪽의 dirty는 유지해 재시도가 가능해야 한다(자식의 기존 규약과 동일 — `plan-form14-specs.tsx:298`).
