## 1. 배경

### 1-1. 사전 안내 경로가 없다

고객에게 "내일 점검하러 갑니다"를 방문 **전에** 알리는 수단이 시스템에 없다. 현재 SMS는 점검현황 모니터링 화면의 수동 발송 하나뿐이고, 그마저 발송 시점이 사람 손에 달려 있다.

### 1-2. 그런데 그 수동 발송이 믿을 수 없는 상태다

착수 전 코드를 실측한 결과 **결함 4건이 한 함수에 몰려 있다**(§2 P-1~P-4). 요지는 하나다 — **실패해도 화면에는 "발송됨"으로 보인다.**

자동 발송은 이 결함을 N배로 키운다. 하루 수십 통이 잘못 나가도 전부 "발송됨"으로 쌓인다. 그래서 이 차수는 **실패 정직 기록을 선결 과제로 두고**(사용자 지시 3-①) 그 위에 사전 안내를 올린다.

### 1-3. 실제로 한 번도 안 나갔을 수 있다

로컬 `.env.local`에 `SOLAPI_API_KEY`·`SOLAPI_API_SECRET`이 **아예 없다**(발신번호만 있음). 키가 없으면 발송은 실패하는데 DB에는 `sms_sent_at`이 찍힌다. 즉 **한 번도 문자가 나간 적이 없는데 "발송됨" 기록만 쌓여 있을 가능성**이 있다. 운영 `.env.production`은 서버 정지 중이라 확인하지 못했다.

### 1-4. 문구를 고칠 자리가 없다

SMS 문구는 컴포넌트에 하드코딩돼 있고 개인 브라우저(localStorage)에만 저장된다(P-6). 직원마다 다른 문구를 쓰게 되고 상호가 바뀌면 재배포가 필요하다.

조사 중 더 넓은 공백이 드러났다 — **관계인 보고 메일 문구는 편집 화면이 아예 없다**(P-7). `message_templates`(마이그레이션 130)와 편집 모달은 이미 있는데, 진입점이 메일 서명 하나뿐이라 나머지 문구는 코드를 고쳐야만 바뀐다.

### 2-5. 기준일 확인 — 방문은 ① 하나뿐

6단계 중 **고객 건물을 실제 방문하는 예정일은 ① 점검표(자체점검)뿐**이다.

|---|---|---|
| ① 점검표 | 현장 점검·점검표 작성 | **있음** |

### 2-6. 중복 발송 위험

같은 고객이 같은 날 **정기 + 자체점검**을 동시에 가질 수 있고, 종합은 1차·2차가 따로 있다(`005_inspection_plans.sql` UNIQUE는 `plan_id+customer_id+sequence_num`이라 다른 계획에 속하면 같은 날이 가능). 선택 단위는 계획 항목인데 **발송 단위는 고객+방문일+번호**다. 접지 않으면 같은 번호로 2~3통 간다. 현재 `saveSmsAction`에는 중복 제거가 **없다**.

## 4. 구현 기안 (전건 미착수 — Q-7)

### 설계 원칙 4가지

**① 발송 경로를 하나로 만든다.** 화면과 크론이 같은 함수를 쓴다. 지금 `pickContact`가 클라이언트에 박혀 있어(P-10) 크론이 재사용할 수 없는 것이 문제의 뿌리다.

**② 고객 단위로 접는다.** 중복 제거를 `groupTargets()` 한 곳에서만 한다. 화면·크론이 각자 접으면 규칙이 갈라진다.

**③ 실패를 지울 수 없게 남긴다.** `inspection_status_log`는 `plan_item_id` UNIQUE라 회차당 1행뿐이라 재발송 이력을 못 담는다. 발송 이력은 **별도 append-only 테이블(`sms_send_log`, 1행 = 1수신자)** 에 쌓고, 화면도 그것을 읽는다. `inspection_status_log`는 은퇴하므로 종전 계획의 `sms_status` 컬럼 추가는 **철회한다**(개정 1판 G-2).

**④ 중복 발송은 DB가 막는다.** "조회 후 제외"(기존 크론 방식)는 이중 발화·동시 클릭에서 샌다. 부분 유니크 인덱스로 강제하고 발송 **전에** `sending` 행을 claim한다. 실패 건은 인덱스에서 빠져 재시도가 된다.

### S5 — 문자 발송 화면 (Q-8·Q-11·Q-12·Q-15) — 모니터링 대체 · **결과 단일 창구**

**상단 승인 배너(Q-12)** — `resolvePendingNotices`가 설정된 시점(`sms_lead_rules`)별로 줄을 만든다:
```
● 내일(8/19) 방문 — 미발송 6곳 · 7통   [대상 보기] [승인·발송]
● 3일 후(8/21) 방문 — 미발송 2곳 · 2통 [대상 보기] [승인·발송]
⚠ 시기 지남 3곳                                    [보기]
```
[승인·발송] = 그 조건으로 필터 + 전체 체크된 모달(S8) 오픈. 결과 0인 날은 "오늘 보낼 안내 없음 ✓" 한 줄. 같은 배너를 대시보드 위젯이 축약해 보여준다.

- **행 = 고객 + 점검일**(발송 단위와 일치 — 계획 항목 단위가 아니다)
- **열**: 고객명 · **점검일(1단계)** · **지역(시/군·읍/면·리)** · 점검유형 · 담당 · 수신자(N명) · 상태 · 발송일시 · 사유
- **점검일 원천은 `scheduled_date`** — `inspection_status_log.inspection_date`(세 번째 값)가 아니다
- 필터: **기간**(기본 오늘~다음 주) · **지역 3단** · 상태(미발송·발송됨·실패·번호없음) · 담당자
- 체크 → [사전안내 발송](S8 모달) · **실패만 필터 → 재발송**
- 조회 원천: `inspection_plan_items`(점검일) ⟕ `customers`(지역·연락처) ⟕ `sms_send_log`(상태)

**지역 3단 (Q-11)** — 시/군(`region_si`) → 읍/면(`region_myeon`) → **리(`region_ri`)**. 앞 단계를 고르면 다음 목록이 그 안의 값만 나오고, 리는 선택 사항이다.

- **리가 필요한 이유** — 양평군처럼 넓은 군은 읍/면 하나가 커서 `강하면`만으로는 동선이 안 잡힌다. `강하면 · 전수리`까지 좁혀야 한 번 나가서 도는 범위가 된다
- **그룹 헤더** `양평군 · 강하면 · 전수리 (5건)` — 헤더 체크로 **그 지역 전체 선택 → 일괄 발송**. 리가 빈 고객은 `양평읍 (리 없음)`으로 묶어 **숨기지 않는다**(필터에서 빠지면 그 고객만 영영 문자가 안 간다)
- **정렬** 시/군 → 읍/면 → 리 → 점검일
- 인덱스 `(region_si)`·`(region_si, region_myeon)`가 이미 있다(`028_performance_indexes.sql`). 리는 그 접두로 걸러진 뒤 좁히므로 별도 인덱스 불필요(활성 고객 수백 규모)

지도 모달(`monitor-client.tsx:309-358`)은 방문 준비에 쓰이므로 이 화면으로 이식한다.

**잃는 것**: 월별 6단계 진행 표. 대체 경로 — 작업대(회차별 6단계)·점검 업무 목록(진행 단계 열)·달력(마감)·대시보드 위젯. 전부 `inspection_steps` 축이라 값이 갈라지지 않는다.

3. **사이드바** [문자 발송] + 미발송 뱃지 · **대시보드 위젯** "내일 방문 8곳 · 미발송 6곳 [확인하고 발송 →]"

### S10 — 자동 크론 (deferred, Q-12)

**이번 차수에는 만들지 않는다.** 승인 방식이 자동의 준비 단계다 — 배너가 쓰는 `resolvePendingNotices`를 크론이 그대로 부르면 되므로, 켤 때 필요한 것은 라우트 1개 + (그때) 멱등 유니크 인덱스 마이그레이션뿐이다.

켤 때의 설계 메모(보존): 인증은 `if (!cronSecret || ...) return 401`(P-9 — 기존 크론의 `if (cronSecret && ...)` 패턴은 미설정 시 무인증 통과라 베끼지 않는다) · 과거 방문일 400 · 키 없을 때 `failed` 행 + `{ok:false, reason:'SOLAPI_CREDENTIALS_MISSING'}`(HTTP 200) + manager 인앱 알림 · VPS 한 곳만 등록(vercel.json 금지 — 이중 등록 = 이중 발송).

## 7. 위험 요소

| 위험 | 대응 |
|---|---|
| 정기 포함이라 발송량이 크다(Q-1) | **승인 방식(Q-12)이 1차 방어** — 통수가 버튼에 찍힌 뒤에만 나간다. + `SMS_MAX_PER_RUN`·allowlist·dry-run |
| 오발송·중복 발송 | 승인 확인 1회 + 화면 '이미 발송됨' 배지 + 상한·allowlist. (유니크 인덱스는 크론 도입 시 — G-11) |
| **모니터링 폐지가 과했을 경우** | 6단계 표 수요가 남으면 점검 업무 목록에 열로 흡수 가능(`inspection_steps` 축). 테이블·데이터 보존이라 되돌릴 수 있다 |
| 수신자 멀티로 문자량 증가 | 미지정 고객은 폴백 1명(종전과 동일) + 화면 통수는 수신자 수 기준 |
| 리 데이터가 빈 고객 | '리 없음' 묶음으로 **숨기지 않는다** — 필터에서 빠지면 그 고객만 영영 문자가 안 간다 |
| 발신번호 미등록 → 전건 실패 | 실발송 1통으로 먼저 확인. 실패도 `failed`로 남아 재시도 가능 |
| Solapi 응답 스키마 가정 오류 | 순수 함수 분리 + `provider_raw` 원문 저장. 인식 실패는 `unverified` — `failed`로 두면 실제 나간 문자를 재발송한다 |
| LMS 전환 비용 2~3배 | 기본 문구 62바이트 설계 + 모달·설정 화면 실시간 표시 |
| 기존 localStorage 문구 소실 | 141 시드를 Q-3 확정 문구로 넣어 기본값 사용자는 무영향. 커스텀 사용자는 배포 전 안내 |
| 개인정보 | API 응답·로그의 번호는 `maskPhone`. `sms_send_log` 쓰기는 service role만 |
