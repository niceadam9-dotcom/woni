## 3. 결정 4개 — 권장안과 고르면 바뀌는 것

### 결정 1. 워크스페이스(테넌트를 어떻게 가르나)

| 선택지 | 장점 | 비용 |
|---|---|---|
| **A. 단일 주소 + 로그인한 계정으로 테넌트 확정 (권장)** | 코드 변경 최소(JWT에 `tenant_id`), 도메인·인증서 1개, 모바일 앱 무변경 | 테넌트별 주소 브랜딩 없음 |
| B. 서브도메인(`회사.제품.kr`) | 업체별 주소로 브랜딩 | 와일드카드 DNS·TLS, 쿠키 범위, `proxy.ts` 호스트 분기, 모바일 앱에 주소 선택 |

권장 이유: 사용자는 한 회사에만 속한다(대행업체 직원이 두 업체를 오가지 않음). B는 나중에 얹을 수 있지만 A→B 이전은 쉽고 B→A는 의미가 없다.

### 결정 2. 문자(SMS) 계정 소유

| 선택지 | 장점 | 비용 |
|---|---|---|
| **A. 운영사 Solapi 계정 + 테넌트별 발신번호 등록 (권장)** | 테넌트는 설정 없이 바로 씀. 문자비를 사용량으로 과금(`usage_events`) | 발신번호마다 통신서비스 이용증명원 서류를 운영사가 받아 등록(테넌트당 1회). 스팸 신고 책임이 운영사 계정에 걸림 |
| B. 테넌트가 자기 Solapi API 키 입력 | 운영사 책임·서류 0 | 소규모 업체에 「API 키 발급」은 진입 장벽. 키 암호화 보관 필요. 문자비 매출 없음 |

권장 이유: 대상 업체(점검원 수 명~십수 명)는 API 키를 다루지 못한다. 다만 **운영사 계정의 일일 상한(`daily_cap`)과 DRY_RUN을 테넌트별로** 두는 것이 전제(로드맵 Stage 2 `tenant_sms_settings`). 큰 업체가 원하면 B를 옵션으로 열 수 있게 설계는 둘 다 받는다.

### 결정 3. 점검표 마스터(약 860항목)

| 선택지 | 장점 | 비용 |
|---|---|---|
| **A. 전역 법정 마스터 + 테넌트 오버라이드 (권장)** | 법 개정을 **한 번 고치면 전 테넌트 반영** — 이게 SaaS의 핵심 판매 문구(준비 목록 §7) | 「오버라이드 없으면 전역」 조회 헬퍼 1개, 캐시 태그에 tenantId |
| B. 테넌트마다 전체 복제 | 테넌트가 자유롭게 고침 | 법 개정 때 N벌 수정 + 충돌 관리, `law-revision-check` 팬아웃 |

권장 이유: 점검표는 법정 서식이라 업체가 바꿀 여지가 작다. 업체 차이는 문구·순서 정도라 오버라이드로 충분.

### 결정 5. 과금 — 두 개로 나눠 답한다

**5-1. 과금 단위**

| 선택지 | 장점 | 비용 |
|---|---|---|
| **A. 대상물(관리 고객) 수 구간 플랜 (권장)** | 업체의 매출과 비례 — 업체가 납득하기 쉽다. 점검원을 늘려도 비용이 안 늘어 현장 전원이 씀 | 구간 경계(예 ~50·~150·~400곳) 정해야 함 |
| B. 사용자(좌석) 수 | SaaS 관행, 계산 단순 | 업체가 계정을 돌려 쓰게 된다(감사 기록 무력화) |

**5-2. 결제 방식**

| 선택지 | 장점 | 비용 |
|---|---|---|
| **A. 계좌이체 + 월 세금계산서 기본, 카드는 옵션 (권장)** | 국내 B2B 소규모 업체 관행. B2(홈택스 일괄발급)를 그대로 재사용 | 미수 관리 수작업(테넌트 수가 적은 초기엔 문제 아님) |
| B. 카드 자동결제(토스 빌링키) 필수 | 미수 0, 자동 해지 | PG 계약·통신판매업 신고·결제 실패 처리 개발(Stage 3 +1~2인주) |

권장 이유: 초기 2~10곳은 손으로 청구해도 된다. 카드 자동결제는 테넌트가 늘 때 Stage 3 안에서 추가.
