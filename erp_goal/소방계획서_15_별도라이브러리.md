## 1. 배경·결정사항

### 1-1. 점검 결과 (#10)
"다른 고객에서 복사"는 전체 복사가 아니었다. 실제 커버리지는 4곳뿐:

#6에서 지적된 "2장·3장 칩 없음"은 버그가 아니라 미구현이었다. 또한 1.5/1.6/1.11 복사는 **확인 없이 기존 입력 전체 덮어쓰기 + 즉시 DB 저장**이라 입력 유실 위험이 있었고, 1.5/1.6은 건물 고유 사실(계단 개소·수전용량·가스 위치 등)이라 타 고객 복사 자체가 데이터 오염이었다.

### 1-2. 결정 (2026-08-10 사용자 확정)
1. **"다른 고객에서 복사" 전면 폐지** — 칩 4곳 + 서버 액션 + 컴포넌트 삭제 (A안, 반영 완료 — 커밋 720efd1)
2. **공통 서술 라이브러리 도입 — pull 방식** (#11): 서술형 섹션만 공통 항목에서 선택해 가져온다
3. **push(라이브러리 → 고객 일괄 반영) 재분류**: **즉시 덮어쓰기 push는 제외** — 라이브러리 수정이 이미 생성·제출된 HWP/PDF와 소리 없는 불일치를 만들기 때문. **개정 알림형 push는 로드맵 편입**(§7) — 전제인 출처 기록(§3-2)을 지금 남긴다
4. **별도 라이브러리 관리 페이지 없음**: 등록·이름변경·삭제·기본지정 전부 각 서식 안에서 처리 (§4)

### 1-3. 문제 분리 — pull이냐 push냐가 아니다 (2차 개정)

세 개의 서로 다른 고통이 "복사 기능"이라는 한 단어에 뭉쳐 있었다. 해법도 서로 다르다.

| 고통 | 실제 크기 | 맞는 해법 | pull로 풀리나? |
|---|---|---|---|
| **신규 작성 반복** — 고객마다 8개 서식을 하나씩 채움 | 활성 고객 약 312곳 × 서식 8개 | **기본항목 자동주입**(§4-0) | ✗ 클릭이 8회 남는다 |
| **문구 개정 전파** — 공통 문구를 고쳐도 기존 고객은 옛 문구 | 라이브러리 항목 수정 시마다 | **개정 알림형 push**(§7) | ✗ 경로 자체가 없다 |
| **고객별 변형 선택** — 용도·규모별로 다른 서술 | 작성 시점마다 | **pull + 리스트 선택**(§4-1) | ✓ |

즉 pull은 세 고통 중 하나만 푼다. pull만 만들면 나머지 둘이 그대로 남고, 즉시 덮어쓰기 push를 만들면 두 번째를 풀면서 새 사고를 낸다. **pull을 뼈대로 하되 ①자동주입으로 반복을 없애고 ②출처를 남겨 개정 전파 경로를 열어두는 것**이 이 문서의 확정안이다.

### 1-4. 추가 확정 (2026-08-10 사용자 확정, 3차 개정)

> **정정 ① `evacPlan.assembly`는 라이브러리 대상이 아니다** (3차 개정, 코드 실측)

> `TrainingDetailRow = { name, at, place, target, kind, form, materials, plan }`(`plan-form111.tsx:12`) — `at`(일시)·`place`(장소)가 섞여 있다. 라이브러리 body에는 이 둘을 **저장하지 않고**, 적용 시 빈 값으로 행을 만든다.

### 2-1. 함께 드러난 기존 결함 — 3.6은 빈 칸이 문서에서 사라진다 (3차 개정)

같은 모양의 화면인데 한쪽만 인쇄된다. 사용자는 회색 표준 문구를 보고 "이미 들어 있다"고 여기지만 3.6은 제출 문서에서 통째로 빠진다.

## 3. 저장 설계 — 마이그레이션 119

### 3-1. `plan_text_library` (공통 항목)

```sql
-- 119_plan_text_library.sql
CREATE TABLE IF NOT EXISTS plan_text_library (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  section_key TEXT NOT NULL,              -- §2의 섹션 키 (training·fireworkLog·…·vulnerableMethods)
  title       TEXT NOT NULL,              -- 항목 이름 (예: "아파트용 훈련 시나리오")
  body        JSONB NOT NULL DEFAULT '{}',-- 섹션별 부분 값 (§2 '라이브러리 대상' 필드만)
  is_default  BOOLEAN NOT NULL DEFAULT FALSE,  -- 자동주입 대상 (§4-0)
  version     INT  NOT NULL DEFAULT 1,          -- body 수정 시 +1 — 개정 알림 판정 기준 (§7)
  bundle_id   UUID,                              -- 서술 세트(§4-4, 로드맵 L-3) 자리만 확보
  sort_order  INT  NOT NULL DEFAULT 0,
  is_active   BOOLEAN NOT NULL DEFAULT TRUE,
  updated_by  UUID REFERENCES profiles(id) ON DELETE SET NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_plan_text_library_section ON plan_text_library (section_key, is_active, sort_order);
-- 섹션당 기본항목은 최대 1개 — 자동주입이 무엇을 넣을지 모호해지면 안 된다
CREATE UNIQUE INDEX IF NOT EXISTS uq_plan_text_library_default
  ON plan_text_library (section_key) WHERE is_default AND is_active;
ALTER TABLE plan_text_library ENABLE ROW LEVEL SECURITY;
-- 접근은 서버 액션(createAdminClient)만 — 096_fire_plan_forms.sql 관례와 동일
```

- 관례: `096_fire_plan_forms.sql` 패턴 (IF NOT EXISTS, RLS enable, ON DELETE SET NULL)
- 삭제는 `is_active=false` 소프트 삭제 — 가져간 고객 데이터에는 영향 없음(pull 시점 복사이므로 참조 없음)
- `version`은 **body가 실제로 바뀔 때만** 올린다. 이름변경(rename)·기본지정은 올리지 않는다 — 안 그러면 문구가 그대로인데 개정 배지가 뜬다
- 대안 검토: 프리셋처럼 Storage JSON(`fire-plans` 버킷 `_presets/*.json` 패턴)도 가능하나, 동시 편집·수정 이력·불변식 검사에 약해 **테이블 채택**

### 3-2. `plan_text_applied` (출처 스탬프)

"이 고객의 이 섹션은 어떤 공통 항목의 몇 버전에서 왔는가"를 남긴다. **지금 pull만 만들더라도 이 기록은 함께 남겨야 한다** — 나중에 개정 알림형 push(§7)를 만들 때 소급이 불가능해지기 때문이다(기록 없는 과거 pull은 영원히 추적 불가).

```sql
CREATE TABLE IF NOT EXISTS plan_text_applied (
  customer_id     UUID NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  section_key     TEXT NOT NULL,
  library_id      UUID REFERENCES plan_text_library(id) ON DELETE SET NULL,
  library_version INT  NOT NULL,           -- 가져간 시점의 plan_text_library.version
  source          TEXT NOT NULL,           -- 'pull'(가져오기) | 'default'(자동주입) — 3차 개정 확정
  applied_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  applied_by      UUID REFERENCES profiles(id) ON DELETE SET NULL,
  PRIMARY KEY (customer_id, section_key)   -- 섹션당 최신 출처 1건 (덮어쓰기)
);
CREATE INDEX IF NOT EXISTS idx_plan_text_applied_library ON plan_text_applied (library_id);
ALTER TABLE plan_text_applied ENABLE ROW LEVEL SECURITY;
```

**왜 `fire_plan_forms.sections` 안에 넣지 않는가** (코드 확인 결과):
1. `saveFirePlanSectionsAction`은 `FORM_SECTION_KEYS` **화이트리스트로 patch 키를 검증**한다(`fire-plan-form-actions.ts:64`). 스탬프 키를 넣으려면 화이트리스트를 뚫어야 하고, 그 순간 **클라이언트가 자기 출처를 위조**할 수 있다. 스탬프는 서버가 기록해야 하는 값이다.
2. `sections`는 서식 저장 시 **통째로 병합·upsert**된다(같은 파일 68행). 서식 저장이 스탬프를 밀어낼 수 있다.
3. §7이 필요로 하는 질의는 **역방향**("이 항목을 쓰는 고객 목록")이다. JSONB 안이면 전 고객 스캔, 별도 테이블이면 `idx_plan_text_applied_library` 한 방.

스탬프 테이블 하나가 **세 가지 역할**을 겸한다: ①출처 추적 ②자동주입 1회성 가드(§4-0) ③(로드맵) 개정 알림 대상 조회(§7).

**기록 시점** (3차 개정 확정):
- **pull(가져오기)**: 가져오기 적용 시점이 아니라 **서식 [저장] 성공 시점**에 기록(`source='pull'`). 가져오기는 폼 상태만 바꾸므로, 적용 즉시 기록하면 저장하지 않고 떠난 경우 거짓 출처가 남는다
- **자동주입**: 서버가 주입·저장하는 시점에 즉시 기록(`source='default'`) — §4-0
- 사용자가 가져온 뒤 문구를 직접 고쳐 저장해도 출처는 유지 — §7 배지에서 본문 해시 비교로 "수정됨" 구분

## 4. UI 설계 — 관리 페이지 없음, 서식 안에서 전부 처리

각 대상 서식 헤더(§2의 8개 카드)에 칩 2개를 추가한다. 기존 `SectionCopyButton` 자리(우측 `ml-auto`)를 그대로 쓴다.

### 4-0. 기본항목 자동주입 — 클릭 0회 (3차 개정: 서버 저장 방식으로 확정)

가져오기 버튼을 아무리 잘 만들어도 고객 312곳 × 서식 8개면 클릭이 남는다. **기본항목은 사용자가 부르기 전에 이미 들어가 있어야 한다.**

- 소방계획서 탭 진입 시 서버 액션(`applyPlanTextDefaultsAction`)이 8섹션을 일괄 검사해, `is_default` 항목이 있고 **스탬프가 없고**(§3-2 가드) 해당 필드가 **빈** 섹션에만 주입·**DB 저장**한다
- **서버 저장인 이유** (2차 개정의 "폼 상태만" 방침을 변경): 자동주입 값이 DB에 없으면 생성 문서에 실리지 않아 §2-1 결함(3.6 미인쇄)을 못 고친다. "빈 칸만 + 고객×섹션당 1회만"이라 유실 위험이 0이고, 1.1 `autoApplyLedgerEmptyAction`(`fire-plan-info-actions.ts:320-377`, 탭 진입 자동·빈 칸만·`ledger_synced_at` 1회 가드)과 정확히 같은 선례다
- **빈 칸 판정**: Record형(brigadeTeams·vulnerableMethods)은 키별로 빈 키만, 문자열(scenario·procedure)은 빈 값일 때만, 행 배열(기록부·details)은 **0행일 때만** 주입
- **1회성**: 주입 시 `plan_text_applied`에 `source='default'` 스탬프 → 사용자가 지우고 저장해도 재주입하지 않는다 (사용자 의사 존중)
- 주입 완료 시 상단 안내: "✅ 공통 기본 서술 N개를 채웠습니다 (빈 칸만) — 각 서식에서 확인·수정하세요"
- 기본항목 지정/해제는 가져오기 팝오버 안에서 ⭐ 토글 (관리 화면 여전히 0개)
- 기본항목이 없는 섹션은 아무 일도 일어나지 않는다 — 도입 초기 안전 기본값

### 4-1. [공통에서 가져오기]
1. 클릭 → 해당 `section_key`의 활성 항목 리스트 팝오버 — **여러 항목 중 선택** (#11 "여러 리스트에서 선택" 요구 반영)
   - 각 행: ⭐기본 표시 · 이름 · **본문 앞 40자 미리보기** · 수정일 — 이름만으로는 "아파트용"과 "아파트용2"를 구분할 수 없어 미리보기가 필요하다
   - 정렬: ⭐기본항목 → 최근 수정 → 이름순
2. 항목 선택 → **폼 상태에만 채움. DB 저장하지 않음** — 사용자가 검토 후 [저장]을 눌러야 반영
   - 구 복사 기능의 "즉시 저장 덮어쓰기" 문제를 설계로 차단
   - `dirty=true`로 표시해 미저장 이동 확인창(unsaved-nav)이 정상 작동 — [저장하고 이동]도 그대로 탄다
3. 적용 방식은 §2 표의 "적용 방식" 열을 따른다 (3차 개정 확정):
   - **치환형**(training.scenario·brigadeTeams·evacPlan.procedure·vulnerableMethods): 해당 필드에 기존 입력이 있으면 인라인 확인("기존 서술을 덮어씁니다") 후 적용
   - **추가형**(기록부 4종·training.details): **기존 행은 그대로 두고 템플릿 행을 뒤에 추가**. 확인창 불필요(유실이 없다). 추가된 행의 고객 고유 칸(date 등)은 빈 값
4. §2 '라이브러리 대상' 필드만 병합 — 고객 고유 필드(인원·일자·기록)는 건드리지 않음
5. 적용 필드는 앰버 하이라이트 + "'{항목명}'에서 가져옴" 툴팁 (1.1 [추천값 채우기]의 `suggested` 패턴 재사용 — `fire-plan-info-panel.tsx:206-208`)
6. 서식 [저장] 성공 시 `stampPlanTextAppliedAction` 호출(§3-2) — 각 폼 `save()`가 `Promise<boolean>`을 반환하므로(커밋 27340e2) 성공 분기 한 줄

### 4-2. [공통으로 등록]
1. 클릭 → 이름 입력(기본값: "{고객명} {서식명}") → 현재 폼의 '라이브러리 대상' 필드만 추출해 저장
2. 같은 이름이 있으면 "덮어쓰기 / 새 항목" 선택 — 덮어쓰기는 body가 실제로 달라졌을 때만 `version+1`
3. 가져오기 팝오버 안에서 항목별 ✏(이름변경)·🗑(삭제, is_active=false)·⭐(기본지정) 제공 → **별도 관리 화면 0개**

### 4-4. 서술 세트(번들) — 8섹션 한 번에 (로드맵 L-3)

§4-0의 자동주입이 기본항목 하나만 다룬다면, 세트는 **"아파트용 표준 서술"처럼 8섹션 조합에 이름을 붙인 것**이다. 신규 고객 작성이 사실상 1클릭이 된다.

- 진입점: 소방계획서 트리 상단 [공통 서술 세트 가져오기] 1개 (서식마다 열 필요 없음)

- 적용도 동일 규약 — 빈 칸만/폼 상태만, 섹션별 적용 결과 요약 후 사용자가 각 서식에서 저장
- **왜 미루나**: 어떤 조합이 실제로 반복되는지는 항목이 쌓여봐야 안다. 지금 조합을 상상해 스키마를 굳히면 안 쓰는 세트 UI만 남는다. `bundle_id` 자리만 미리 비워둬 나중 확장 비용이 거의 없다

## 5. 서버 액션 설계 — `plan-text-library-actions.ts` 신설 (3차 개정: 8종 확정)
