## 3. ② 확인 결과 — 자동 체크는 **현재 없다**

`fire_facilities`에 **쓰는** 코드는 전 저장소에서 **단 한 곳**이다:

- `facilities-actions.ts:42` (`delete`) + `:45` (`insert`) — 1.4 저장 액션
- 그 외 전 등장은 `select`/`count`. 점검표 저장 액션도 읽기만 한다 (`sheet-actions.ts:51`)
- `customers/actions.ts:1428`은 삭제 전 행수 세기(읽기)

그리고 반대 방향으로 **정책이 이미 확정돼 있다** — `sheet-facility-map.ts:363-368`:

> 미설치 = 무조건 ／ (2026-09-03 사용자 결정, image-51 강순건물). 1.4 대장 체크가 점검결과의
> 정본 축이다: **미체크 항목은 응답이 있어도 ／로 인쇄한다.**

즉 순서를 뒤집으면 1.4로 올라가지 않을 뿐 아니라 **채운 값이 문서에서 ／로 눌린다.**
자동 체크가 없는 것은 누락이 아니라 **결정**이다.

> ⚠ **이 절은 「현재 상태」의 기록이다 — 금지 조항이 아니다.** 이 문서 첫 판은 여기서
> "앞으로도 넣으면 안 된다 · 범위 밖"이라고 결론 냈으나, **2026-09-11 사용자 요구 ③으로
> 뒤집혔다**(§9). 자동 체크를 설계하는 쪽은 §9를 읽을 것. 이 절은 그때 무엇을 뒤집는지를
> 알기 위해 남겨 둔다 — 2026-09-03 결정의 **원인이 실제 사고**였다는 사실이 §9-1의 방어 규칙을
> 정당화한다.

### 3-1. 반자동 경로 하나 — 자동이 아니다

`plan-form14.tsx:609-627` `[모두 설치로 체크]` (소방계획서_40 S6). 제약이 넷:

1. 1.4 화면에 들어가야 보인다 (점검표 화면에는 이 경고가 없다)
2. `canManage` 권한이 필요하다
3. 체크만 바꾸고 **저장을 따로** 눌러야 한다
4. **○·× 응답이 있을 때만** 뜬다 — 전부 ／면 침묵 (`sheet-facility-map.ts:408-413`)

### 3-2. 🚨 정정 — 「1.4가 비면 회색이라 입력이 막힌다」는 **틀렸다**

초안(이 문서 첫 판)은 "1.4가 비면 그 중분류는 회색이라 입력 자체가 막혀 ○·×를 만들 수 없다"고
적었다. **실측 결과 정확히 반대다.** `sheet-actions.ts:75`:

```ts
if (!sheetName || !sheetMatchesFacilities(sheetName, facilityCodes)) return out
```

`:61` 주석이 규약을 명시한다 — **"시트째 미설치면 빈 집합. 중분류 축은 설치 시트 안에서만 좁힌다."**
`notInstalled`는 이 집합에서만 나온다(`:198`). 따라서:

| 1.4 상태 | 회색 | 입력 | 저장 | 인쇄 |
|---|---|---|---|---|
| **완전 미입력**(전 시트 미설치) | **안 걸림** | **가능** | **됨** | ／ (대장 정본) |
| 부분 입력 · 시트 설치 · 중분류 미설치 | 걸림 | 불가 | 걸림 | ／ |

즉 **「점검표를 먼저 입력」 시나리오에서는 입력이 막히지 않는다.** 응답이 DB에 실제로 남고,
`respondedNotInstalled` 경고도 실제로 뜬다. 회색 축이 무는 것은 1.4를 **이미 만진 뒤**의
부분 상태뿐이다 — 그건 「먼저 입력」이 아니다.

⚠ 이 정정이 §9를 가능하게 한다. 자동 체크의 트리거가 될 응답이 실제로 생기기 때문이다.
초안의 오판을 남겨 두는 이유는, 「막혀 있다」는 전제로 설계를 다시 세우면 §9가 불가능하다고
결론 내게 되기 때문이다.

## 4. 왜 안내만으로는 부족한가 — 안전장치가 전부 동시에 침묵한다

`sheet-overview.ts:403-405`가 미설치 시트를 필수 집계에서 빼기 때문에, 설치 축이 비면
**분모가 0이 되고 분모에 의존하는 경고가 한꺼번에 꺼진다**:

| 장치 | 1.4 입력됨 | 1.4 미입력 |
|---|---|---|
| 필수 미입력 카운터 (`sheet-entry-client.tsx:407`) | N건 표시 | **0 — 침묵** |
| 이탈 확인 팝업 (`:392`, 조건 `requiredBlank > 0`) | 뜸 | **안 뜸** |
| 단계 완료 보류 (`inspection-step-sync.ts:143-158`) | 보류 | **통과 → `completed` DB 기록** |
| 별지 생성 경고 (`report9-assemble.ts:962`) | 경고 | **침묵** |

**핵심 결함**: 1.4를 건너뛴 사용자에게는 "다 채웠다"는 초록 신호가 뜬다. 나중에 1.4를 채우면
분모가 늘어 미입력이 생기는데, 단계는 이미 완료로 남는다. 경고가 없어서 조용한 게 아니라
**경고를 만드는 분모가 없어서** 조용하다 — 공허 통과다.

## 5. 결정적으로 유리한 조건 둘

### 5-1. 미입력과 「해당 설비 없음」을 구별할 수 있다

`buildings.facilities_verified_at`이 **저장·확인 양쪽** 경로에서 찍힌다
(`facilities-actions.ts:61` `saveFacilitiesAction` / `:87` `verifyFacilitiesAction`).
NULL = 한 번도 손댄 적 없음.

⚠ 기존 `noFacilityInfo`(`sheet-overview.ts:313`)로는 안 된다 — 그건 `installed` 0건만 보므로
「미입력」과 「설비가 정말 없음」을 **뭉갠다**. 오탐 0을 원하면 `verified_at`을 읽어야 한다.

### 5-2. 우회로가 이미 있어서 하드 게이트가 안전하다

`verifyFacilitiesAction`(= 1.4 화면 `[변경 없음 확인]`) 한 번이면 NULL이 풀린다.
설비가 정말 없는 대상물도 **1클릭이면 통과**하므로, 강하게 막아도 사용자를 가두지 않는다.
이것이 차단형을 권하는 근거다 — 게이트에 반드시 이 버튼을 같이 달아야 성립한다.

### 5-3. 왕복 경로도 이미 완성돼 있다 — 새 화면 0개

`/inspections/{id}/facilities`(`facilities/page.tsx`)가 점검 문맥 안에서 1.4 정본 컴포넌트를
그대로 서빙하고, `?from=`으로 점검표에 복귀하며(`:55`), 저장 시 점검표 경로까지
revalidate한다(`facilities-actions.ts:73-75`). **만들 화면이 없다.**

## 6. 설계안 — 3층, 핵심은 ②

### ① 예방 (진입 전)

회차 카드 `[점검표 입력]`(`plan-annex-round-card.tsx:110`) 옆에 「1.4 미확인」 배지.
누르면 점검표가 아니라 `/inspections/{id}/facilities?from=…`으로 보낸다.

### ② 관문 (진입 시) — 핵심

점검표 화면 최상단 차단 배너 + 시트 목록 가림. 버튼 둘:

- `[1.4 소방시설 먼저 입력하기]` → `/inspections/{id}/facilities?from=/inspections/{id}/sheet`
- `[해당 설비 없음 — 확인만 하기]` → `verifyFacilitiesAction` (§5-2)

판정: **활성 동 전부** `verified_at IS NULL`일 때만 차단. 일부만 NULL(다동)이면
차단 없이 경고 줄만 — 「N개 동의 설비 현황이 미확인입니다」.

자리는 기존 배너 슬롯(`sheet-entry-client.tsx:441-470`, 지난 회차 제안·stale 배너와 같은 줄).

### ③ 최후 방어 (완료 시)

`inspection-step-sync`에서 1.4 미확인이면 ① `completed` 전환 보류.
화면을 우회해 액션을 직접 호출해도 **잘못된 완료가 DB에 박히지 않는다**(§4의 3행).
필수 미입력 보류(`:143-158`)와 **같은 자리·같은 패턴**이라 새 개념이 없다.

### 6-1. 구현 비용 — 쿼리 왕복 추가 0회

`sheet-overview.ts:166-167`의 buildings 조회가 **이미 활성 동을 읽고 있다**:

```ts
.select('id, customer_id').in('customer_id', customerIds).eq('is_active', true)
```

여기에 `facilities_verified_at` 컬럼 하나를 더하고, `SheetOverview`에
`facilitiesUnverified: { total: number; unverified: number }`를 실으면 끝이다.
`countRequiredItemBlanks` 쪽(`:385-389`)도 같은 방식.

⚠ 판정식은 **한 곳**에만 둔다(`lib/`의 순수 함수로 승격). 배너·배지·step-sync 세 표면이
각자 세면 갈라진다 — 소방계획서_39의 `countRequiredItemBlanks` 단일 원천과 같은 이유다.

## 8. 검사 계획 — 이 축을 단언하는 검사가 현재 **0건**이다

🚨 1.4 미입력 상태를 만드는 픽스처가 없어, 지금 스위트는 **어느 쪽으로 고쳐도 초록**이다.
구현과 검사 신설이 같이 가야 한다.

핵심 단언은 「막는가」가 아니라 **「막으면 안 될 때 안 막는가」**다(소방계획서_47 B-15·
건물 중복 확인 차수와 같은 교훈):

1. `verified_at` NULL + 활성 1동 → **차단**
2. `verified_at` 있음 + `installed` 0건(= 설비 정말 없음) → **차단 안 함** ← 가장 중요
3. 다동 부분 NULL → **차단 안 함**, 경고 줄만
4. `[해당 설비 없음 — 확인만]` 누른 직후 → 같은 화면에서 차단 해제
5. NULL 상태에서 점검표 응답을 다 채워도 ① `completed` 안 됨 (§6 ③)
6. `verified_at` 채운 뒤 같은 응답으로 ① `completed` 됨 (5의 양성 대조)

⚠ 5·6은 **쌍으로** 넣는다 — 음성만 넣으면 양성 경로가 한 번도 안 돈다(소방계획서_48의
6→4→3 교훈). 변이 실험으로 각 단언이 실제로 무는지 확인할 것(초록은 증거가 아니다).

## 9. 방향 반전 — 점검표 입력이 1.4를 자동 체크한다 (2026-09-11 추가 요구)

> ③ "점검표를 먼저 입력해도 1.4는 자동체크되게 제안해줘"

§3의 「자동 체크는 없다」를 **바꾸라**는 요구다. §6의 관문(막기)과 방향이 반대이지만 목적은 같다 —
**두 축이 어긋난 채 문서가 나가는 것을 막는 것.** 관문은 사람을 돌려보내고, 자동 체크는
시스템이 따라잡는다. 둘은 배타적이지 않다(§9-6).

### 9-1. 무엇을 뒤집는가 — 정직하게

이 요구는 2026-09-03 결정(`sheet-facility-map.ts:363-368` 「미설치는 응답이 있어도 ／」)을
**형식적으로는 유지하되 실질적으로 무력화**한다. 대장이 정본인 것은 그대로지만, 그 대장을
점검표가 쓰기 때문에 ／로 눌릴 일이 없어진다.

그래서 **되살아나는 위험을 명시해 둔다** — 이 규칙이 생긴 원인이 실제 사고였다:

| 날짜 | 사고 | 자동 체크에서 재발하는가 |
|---|---|---|
| 2026-08-20 | 체크 없는 화재조기진압용·할론·화재알림설비에 ○ (실측 7건 12칸) | **재발 가능** — 오탭 1건이 대장에 설치를 박는다 |
| 서림사 | 유도등·유도표지를 전부 ／로 넣었는데 피난유도선의 ○ 때문에 세 칸 모두 ○ | **방어 가능** — §9-3 중분류 귀속 |

종전에는 **인쇄 단계에서 ／로 눌러** 막았다. 자동 체크는 그 안전망을 치운다. 따라서 방어는
인쇄가 아니라 **입력 지점**에 있어야 한다 — 그게 §9-3의 세 규칙이다.

### 9-2. 이미 계산돼 있다 — 새 판정식 0개

`rollUpForm3Results`(`sheet-facility-map.ts:374-416`)가 **이미 답을 낸다**:

```ts
axisWarnings.respondedNotInstalled = [...statByItem]
  .filter(([it, st]) => !installed.has(it) && (st.o || st.x)).map(([it]) => it)
```

이 배열이 곧 **자동 체크 대상**이다. 새 함수를 쓰면 판정이 두 벌이 된다 — 반드시 이걸 쓴다.
그리고 이 식이 §9-3의 규칙 ①②를 **이미 품고 있다**(`:408-409` 주석이 그 이유를 적어 뒀다).

### 9-3. 세 규칙 — 이걸 어기면 사고가 재발한다

**① ／는 트리거가 아니다.** `(st.o || st.x)` — ／는 "해당 없다"는 **진술**이라 설치 근거가 아니다.
전부 ／인 시트를 근거로 대장에 설치를 넣으면 사용자 진술의 반대를 기록하는 셈이다.

**② 형제에게 번지지 않는다.** 귀속은 **중분류 단위**다(2026-09-01에 시트→중분류로 옮긴 그 축).
시트 단위로 귀속하면 한 시트가 덮는 설비 2~3개가 **한꺼번에** 설치로 켜진다 = 서림사 사고의
자동 체크판. `rollUpForm3Results`에 `withGroups: true` 통계를 넘겨야 이게 성립한다
(`sheet-actions.ts:110-112` 주석 — 1.4 대장 배지가 이미 그 이유로 켜 놓은 옵션).

**③ 이미 `installed=true`면 쓰지 않는다.** 실제 쓰기는 설비당 최초 1회. 매 저장마다 대장을
때리면 공유 트리 경합·감사 로그 소음이 생긴다.

### 9-4. 🚨 `facilities_verified_at`은 절대 자동으로 찍지 않는다

**이 문서에서 가장 중요한 함정이다.** §5-1이 「미입력」 신호로 쓰는 컬럼이 바로 이것이고,
§6의 관문이 그 값으로 판정한다. 자동 체크가 `saveFacilitiesAction`을 재사용하면
`facilities-actions.ts:61`이 **`verified_at`을 함께 찍어** 관문이 스스로 풀린다 —
「사람이 설비 현황을 확인했다」가 거짓이 되고, §6 전체가 조용히 무력화된다.

따라서 자동 체크는 `saveFacilitiesAction`을 **쓸 수 없다**. 이유가 하나 더 있다:
그 액션은 `delete → insert` **replace 방식**이라(`:42`·`:45`, K-5 주석에 소실 리스크가 이미
적혀 있다) 한 행을 켜려고 부르면 그 건물의 설비 전체를 지우고 다시 넣는다.

→ **행 단위 upsert 전용 좁은 액션**을 새로 만든다. `installed`만 쓰고 `verified_at`은 건드리지 않는다.

### 9-5. 되돌릴 수 있어야 한다 — 출처를 남긴다

시스템이 법정 대장을 썼다면 사람이 그것을 알아보고 되돌릴 수 있어야 한다.

- `fire_facilities.detail`(JSONB)에 출처 표시 — 예 `{ auto: '2026년 2차 점검표' }`.
  `detail.note`는 사용자 비고라 **덮지 않는다**(같은 칸을 나눠 쓰므로 키를 분리).
- 1.4 화면(`plan-form14.tsx`)에 「점검표에서 자동 체크됨」 배지 + 해제 경로.
- 사용자가 손으로 저장하면 `saveFacilitiesAction`이 replace하므로 출처 표시는 자연히 사라진다
  (= 사람이 확인한 값으로 승격). 이 동작은 의도된 것이다.

### 9-6. §6 관문과의 관계 — 같이 넣어도 모순이 없다

자동 체크는 `installed`를 채우고, 관문은 `verified_at`을 본다(§9-4). **축이 다르므로 공존한다**:

- 1.4를 안 만지고 점검표부터 → 관문이 차단(§6 ②). 사용자가 `[해당 설비 없음 — 확인만]`을
  누르면 `verified_at`이 찍히고 통과.
- 그 뒤 점검표에 ○/×를 넣으면 → 자동 체크가 대장을 따라잡는다.
- 관문을 ⓑ경고만으로 하면 → 자동 체크가 주 방어선이 된다.

즉 §7 미결정 1번(관문 강도)의 답이 ⓑ여도 이 차수는 성립한다. **다만 §9-4를 어기면
자동 체크가 관문을 죽인다** — 둘을 한 차수에서 같이 구현하는 편이 안전하다.

### 9-7. 미결정 — ✅ 네 건 전부 확정·구현·배포됨 (2026-09-12 · 2026-09-18 정정)

이 절도 낡은 채 남아 있었다. 구현 코드가 결정을 **직접 인용**한다:
`facility-autocheck-actions.ts`에 「§9-7 미결정 2 = **저장 시 즉시**」·「§9-7 미결정 3 =
**허용**」이 적혀 있고, 1번은 `facility-autocheck.ts`의 skip 사유(「켤 수 없었던 이유 —
활성 건물 0동·**다동** 등」)로 **ⓐ(다동은 안 켠다·조용히 넘어가지 않는다)**가 구현됐다.
4번(고지)은 `sheet-entry-client.tsx`의 반영 안내로 구현됐다. 35회차 배포 완결.

| # | 쟁점 | 선택지 | 권장 |
|---|---|---|---|
| 1 | 다동 고객에서 **어느 동**에 체크하나 | ⓐ단동만 자동·다동은 경고 / ⓑ대표동 / ⓒ전 동 | **ⓐ** — 점검은 고객 축, 대장은 건물 축이라 다동은 결정 불가. ⓑ는 `is_primary`가 **미적용**(42703 실측)이라 지금 못 쓴다. ⓒ는 안 쓰는 동에 설비를 박는다 |
| 2 | 시점 | ⓐ저장 시 즉시 / ⓑ회차 완료 시 일괄 | **ⓐ** (§9-3 ③으로 쓰기는 설비당 1회) |
| 3 | 권한 | 점검표 입력자(`inspection_register`)가 대장(`customer_manage`)을 바꾸는 것을 허용하나 | **허용** — `facilities/page.tsx:26-27`이 이미 "대장은 고객 자산"이라며 두 권한을 나눠 넘긴다. 자동 체크는 시스템 행위이고 §9-5로 추적된다 |
| 4 | 고지 | 자동 체크되면 분모가 늘어 **필수 미입력이 갑자기 생긴다** — 알릴까 | **알린다** — 「대장에 N건 자동 반영 · 필수 입력 M건 추가」 토스트. 조용히 늘면 사용자가 이유를 모른다 |

⚠ 1번의 실측이 먼저다. 메모리에 「실측 295/295가 1동」이 있지만 **그건 다른 세션의 측정이고
낡을 수 있다** — 다동 고객 수를 재고 나서 ⓐ의 비용(경고만 받는 고객 수)을 판단할 것.

### 9-8. 검사 — 변이로 무는지 확인할 것

1. ○ 응답 → 그 설비 `installed=true` (양성)
2. × 응답 → 같음 (양성 — ×도 점검한 증거다)
3. **／만 있는 시트 → 체크되지 않음** ← 규칙 ①, 가장 중요
4. **한 시트가 덮는 형제 설비 2개 중 하나만 ○ → 다른 하나는 안 켜짐** ← 규칙 ②, 서림사 사고 회귀 검사
5. **자동 체크 후에도 `verified_at`은 여전히 NULL** ← 규칙 §9-4, §6 관문 생존 검사
6. 이미 `installed=true`면 UPDATE 발행 0회 (규칙 ③)
7. `detail.note`(사용자 비고)가 있는 행을 자동 체크해도 note 무손상
8. 다동 고객 → 자동 체크 안 하고 경고 (미결정 1이 ⓐ로 확정될 경우)

⚠ 3·4·5는 **음성 단언**이다 — 「안 켜지는가」를 묻는다. 3·4는 양성 대조(1·2)와 쌍으로 두고,
5는 §8의 1·2와 교차한다. 초록은 증거가 아니므로 각 단언을 변이로 무는지 확인할 것.

## 10. 확정 — 고객 1 : 건물 1로 고정하고 「건물정보」만 남긴다 (2026-09-11)

> ④ "다동 고객은 없어, 별지와 소방계획서와 동일하게 건물정보만 추가가 되면 돼 제안해줘"

🚨 이게 셋 중 가장 중요하다. 지금은 **고객명만 넣으면 0동**이 되고, 0동이면

### 10-7. 🚨 서식 원문 실측 — 「동」은 두 가지 뜻이고, 사용자 방식이 맞다

> ⑤ "별지서식 내용을 채우기만 하면돼" / ⑥ "구체적으로 별지에 필요한 정보가 무엇인지 확인해줘 다동인 경우"

#### 축 ① 「건물동수」 — 한 대상물이 여러 동일 때

원문 2쪽 「2. 건축물 정보」 표 안에 **칸 하나**가 있다:

```
118| 높 이   119| m   120| 건물동수   121| 개동
```

즉 한 대상물이 3개 동이면 **「3 개동」이라고 한 칸에 적는다.** 나머지 칸(연면적·건축면적·
세대수·층수·높이·구조·지붕·승강기·주차장·계단·경사로)은 **그 대상물 한 세트**뿐이다.

→ ERP에 **이미 필드가 있다**: `building_count`(`building-inline-panel.tsx:733` `bf-building-count`),

(`customers/actions.ts:1871` `building_count: list.length` — 같은 지번 표제부 행 수).

#### 축 ② 「동별」 반복 — 여러 **대상물**을 하나의 서식에 함께 보고할 때

작성방법 ※(`:498`):

> 하나의 소방안전관리대상물에 대한 자체점검 결과를 보고하면서 이 중 **일부 대상물 또는 전체

예외 둘 — **사용승인일은 고객 공통**(동별 아님, `report9-assemble.ts:741`), 특별피난계단은 항상 공란.

#### 결론 — 🚨 §10-1·§10-4의 서술을 정정한다

§10-1은 "법정 서식은 다동을 전제한다 … 작성요령 10 「동별로 나누어 작성」"이라고 적었다.
**부정확하다.** 원문에 「나누어」는 **0회**, 「작성요령」도 **0회**다(절 이름은 「작성방법」).
그리고 조건이 「한 대상물의 여러 동」이 아니라 **「둘 이상의 대상물을 함께 보고하는 경우」**다.

따라서:

| | 서식이 요구하는 것 | ERP 표현 | 사용자 방식에서 |
|---|---|---|---|
| ① 한 대상물 = 여러 동 | **「건물동수 N 개동」 한 칸** | `building_count` 필드 | **충족** — 대장 자동 |
| ② 여러 대상물 함께 보고 | 동별 건축물정보 표 반복 | `buildings` 행 여러 개 | **해당 없음** — 대상물을 별개 고객으로 관리하면 보고서가 각각 나가므로 「함께 보고」를 택하지 않는다 |

**②는 의무가 아니라 선택이다** — "함께 보고하는 경우"가 조건절이고, 12는 대안까지 명시한다.
대상물을 별개 고객으로 두고 각각 보고하는 것은 서식상 정상이다.

→ **§10의 결정이 서식 근거를 얻었다.** 건물 행 추가를 없애도 서식을 못 채우는 칸은 없다.
「건물동수」는 행이 아니라 **칸**이고 이미 있다. §10-4의 「서식은 있는데 채울 길이 없다」는
**②에만** 해당하며, ②는 선택적 구조다.

⚠ 그래도 ②의 코드는 **지우지 않는다**(§10-4). 언젠가 한 고객 안에서 「함께 보고」를 택하면
그때 필요한 것은 **동별 건축물정보 표 한 세트 전부**이지 「건물동수」 칸이 아니다 —
두 축은 서로를 대체하지 못한다.

### 11-1. 🚨 내가 「막혔다」고 오판했다 — 부재 판정을 낡은 HEAD에 댔다

이 문서 앞 판은 §10-2 ②③이 **막혔다**고 적었다. 근거는 공유 트리 `git status`의

```
[??] erp/src/lib/building-panel-open.ts
[??] erp/src/lib/primary-building.ts
```

였고, 여기서 「origin/main에 없는 모듈」이라고 결론 냈다. **틀렸다.**
`git cat-file -e origin/main:<path>`로 재니 **둘 다 origin/main에 있었다.**

`git status`는 **HEAD를 기준으로** 판정하는데, 이 저장소의 로컬 `main`은
`1a8fb78`에서 갈라져 origin보다 **17 ahead / 1 behind**다. 그 HEAD에 그 파일들이 없어서
`??`로 보였을 뿐이다. 즉 **계측기가 낡은 기준을 들고 있었다.**

⭐ 교훈: **부재 판정은 반드시 `origin/main`에도 댄다.** 이 저장소에서 같은 형태의 오판이
이미 기록돼 있었는데(로컬 main이 갈라져 grep이 오판) 내가 그대로 반복했다.
`git diff origin/main -- <untracked>`도 믿을 수 없다 — untracked는 인덱스에 없어
**「전부 삭제」로 보인다**(`0 70`·`0 85`가 그 artifact였다). 디스크 내용 판정은 해시 대조로.

### 11-2. 실제 장애물은 달랐다 — 공유 트리가 갈라져 있다

디스크 해시 대조 결과 `building-inline-panel.tsx`·`building-panel-open.ts`·`primary-building.ts`

→ 그래서 ②③을 **공유 트리가 아니라 격리 워크트리에서** 구현했다(origin/main + 내 커밋).

### 12-4. 검사의 핵심은 「기본값」이 아니라 「달력이 남아 있는가」

🎯 `[C1][C2][C3]` — **달력이 여전히 있고 수정 가능한가.** 「기본값이 오늘인가」만 물으면

실제 변이로 확인: 기본값을 `''`로 되돌리면 `[B9]`·`[B9c]` 빨강·exit 1.

### 12-5. 발견하고 손대지 않은 것

🚨 `recordSubmissionAction`(`timeline-actions.ts`)에 **미래 날짜 검증이 없다** — 형식 검사만 한다.

## 15. 🔄 §10-2 ② 철회 — [+ 건물 등록] 복원 (2026-09-15)

**사용자 요청으로 버튼을 되살렸다.** §10-4가 예고한 바로 그 복원이다("다동이 실제로 오면
이 버튼을 복원하는 것이 정답"). 발단은 갑지 「다수동일때」 시트 화면(`erp_goal/image-15.png`) —
2·3·4동 블록이 실재하는데 **그 칸을 채울 2번째 동을 넣는 문이 화면에 없었다.**

### 15-1. 되돌린 것은 ② 하나뿐

| 항목 | 상태 |
|---|---|
| ② `[+ 건물 등록]` | 🔄 **복원** |
| ③ 「건물정보」 제목 · 1동이면 표 감춤 | ✅ **유지** — 되돌리지 않았다 |
| ① 고객 등록 시 1동 무조건 생성 | ✅ **유지** — 0동 금지는 그대로다 |

셋을 한 묶음으로 기억하면 다음 사람이 함께 되짚는다. **한 줄로 못 박아 둔다: ②만 철회.**

### 15-2. 🚨 복원판은 원본과 다르다 — 조건으로 숨기지 않는다

원본(`cf139d0` 이전)은 `{canManage && editing !== 'new' && (…)}`였고, 당시엔 등록 폼이
**늘 열려 있어** 그 조건이 버튼을 **영원히 숨겼다**. 그것이 「규현빌라」 2중 등록 사고의
배경이다. 그래서 원본 스니펫을 그대로 되살리면 **사고의 배경까지 함께 복원**된다.

복원판은 `canManage`만 보고 **항상 그린다.** 대신 등록 폼이 이미 열려 있을 땐 `disabled`로
**보이되 눌리지 않게** 했다 — 감추면 결함이 재발하고, 아무 가드도 없으면 입력 중이던 새 동이
빈 폼으로 초기화된다. 「조건에 가려 숨는 것」과 「비활성으로 보이는 것」은 다르다.

### 15-3. 검사 — 계약을 지우지 않고 **방향만 뒤집었다**
