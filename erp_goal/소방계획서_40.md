## 1. 발단 (사용자 요구, 2026-09-03)

> "소방계획서 > 시설설비 와 점검표 함께 입력하도록 하는 방안을 검토해줘 그리고 제안해줘"
> "1, 2, 3 통합한 사용자 편리성을 검토해줘" / 범위: "전부 (설치+수량+세부제원)"
> "별도의 화면페이지를 만들어 입력하는 것도 검토해줘" / "아니면 쉽게 왕래 할 수 방법도 제안해줘"
> "반대로 점검표 > 시설설비 도 괜찮고" / 최종: "소방시설 <-> 점검표"

문제: 두 입력은 데이터로는 이미 결합돼 있으나(설치 체크 = 점검표 적용 축, 점검표 결과 = 1.4 배지)
**입력 동선이 갈라져** 있다. 점검표 입력 중 설치 누락을 발견하면 고객 상세 → 소방계획서 탭 → 1.4로
4~6클릭 이동 후 복귀해야 하고, 복귀하면 열었던 시트·월 컨텍스트가 사라진다.

## 2. 방향 비교 (검토 결과 — 사용자 승인 완료)

| 방향 | 판정 | 이유 |
|---|---|---|
| A. 점검표 화면 안에 1.4 드로어 임베드 | **보류(후속 후보)** | PlanForm14가 자체 `fixed inset-0` 오버레이 소유(`plan-form14.tsx:818`) → 드로어 중첩 충돌. 프리로드 시 낡은 기준값으로 전체 저장 위험(1.4는 last-write-wins) |
| B. 1.4 화면에 점검표 병합 | **기각** | 한 화면에 자동저장(300ms upsert)과 폼 전체 저장 두 규칙 공존 — 소방계획서_28이 제거한 사고 구조의 부활(`plan-form14.tsx:680-683` 주석이 명시) |
| **C. 점검 귀속 시설설비 페이지 신설 + 양방향 직행 링크** | **채택** | PlanForm14는 props만 받는 순수 클라이언트 컴포넌트(`:85-92`)라 재사용 비용 최소. RSC 진입마다 신선한 데이터. 저장 액션·컴포넌트 단일성 유지. A로 가는 길도 안 막힘 |

그대로 다른 URL(`/inspections/[id]/facilities`)에서 서빙하고, 두 화면 사이를 `?from=` 딥링크로 잇는다.

## 4. 설계

### S1 — 데이터 조립 헬퍼 추출 (로드 규칙 단일화)

- **S1-1** `src/lib/facility-form-data.ts`(server-only, 신규): `customers/[id]/page.tsx:202-252`의
  3쿼리+매핑(fire_facilities·fire_facility_floors·customer_facility_specs →
  `facilityBuildings`·`specsByBuilding`, receiver_location·emergency_elevator_count 포함)을
  `loadFacilityFormData(admin, customerId)`로 추출.
- **S1-2** 고객 상세 페이지를 이 헬퍼 호출로 교체(기계적 리팩터링, `Promise.all` 유지) —
  두 화면이 다른 초기값을 보는 사고를 원천 차단.

### S2 — PlanForm14 옵션 props (1.4 기본 동작 무변경)

- **S2-1** `inspectionCtx?: { id: string; label: string } | null` — 있으면 회차 자체 페치
  (`getActiveSpecialInspectionAction`, `plan-form14.tsx:165-178`) 생략. 새 페이지가 URL의
  inspection으로 결정적 주입. 미지정이면 종전 동작 그대로(1.4 무변경).
- **S2-2** `linkFrom?: string` — resultBadge(`:253`)·「기타」 링크(`:652`)의 `?from=` 하드코딩
  (`/customers/{id}?tab=plan&form=1.4`)을 대체 가능하게. 새 페이지는
  `/inspections/{id}/facilities?from=…`을 넘겨 배지 클릭→점검표→뒤로가기가 새 페이지로 복귀.

### S3 — 전용 페이지 신설 `/inspections/[id]/facilities`

- **S3-1** `src/app/(dashboard)/inspections/[id]/facilities/page.tsx`(신규, RSC):
  `sheet/page.tsx:28-93` 골격 재사용 — 로그인 게이트 → inspection 조회
  (`customer_id, year, sequence_num, plan_type`) → `loadFacilityFormData` → PlanForm14 마운트.
- **S3-2** 권한은 1.4와 **같은 축**: `can(role,'customer_manage')`=canManage,
  `can(role,'inspection_register')`=canRegister(`customers/[id]/page.tsx:712-713`과 동일 값).
  둘 다 전 직원(employee/manager/admin)이라 공백 없음 — **점검 건 편집권(담당자 축)과 무관하게**
  비담당 직원도 설비 정정 가능(의도된 설계 — 설비 대장은 고객 자산이지 점검 건 자산이 아니다).
- **S3-3** `?from=` 내부 경로 검증(`sheet/page.tsx:77-78` 규칙 복사), 헤더 뒤로가기
  (기본값 `/inspections/{id}/sheet`). `inspectionCtx` label은 `{year}년 {sequence_num}차`.
- **S3-4** 다건물 고객은 PlanForm14 내장 건물 셀렉터·전환 가드(`:330-351`)가 그대로 처리 —
  신규 코드 없음.

### S4 — 저장 후 점검표 설치 축 갱신

- **S4-1** `saveFacilitiesAction`에 `opts?: { alsoRevalidate?: string[] }` 추가(분기 없는
  revalidate 추가 — 저장규칙 단일 유지). 새 페이지는
  `['/inspections/{id}/sheet', '/inspections/{id}/facilities']`를 넘긴다.
- **S4-2** 복귀는 `?from=` 링크 → 시트 페이지 RSC 재실행 → `buildSheetOverviews`가
  fire_facilities를 재조회해 `installed`·`uncoveredFacilityCodes` 자동 갱신
  (`sheet-overview.ts:164-180` — 설치 축은 고객 활성 건물 전체 union이라 어느 건물에 저장하든 반영).
  ⚠ Next 16 클라이언트 라우터 캐시가 revalidatePath로 안 뚫리면 복귀 버튼을
  `router.push(from); router.refresh()`로 — 구현 시 `node_modules/next/dist/docs` 캐싱 문서 확인.

### S5 — 왕래 링크 (양방향)

- **S5-1** **점검표 → 소방시설**: `sheet-entry-client.tsx` 좌측 목록 상단(`:393-402`)과
  uncovered 경고 블록(`:422-429`)에 「설비 현황(1.4) 수정」 링크.
  `?from=`에 **클릭 시점 현재 URL**(sheet·month 포함 — `:202-210` replaceState로 항상 최신)을
  실어 복귀 시 시트·월 재현.
- **S5-2** 링크 노출은 권한 게이트 없이 항상(새 페이지가 canManage로 게이트) — 점검 건 편집권
  없는 사용자도 설비 정정 경로는 열려야 한다(S3-2와 한 몸).
- **S5-3** **소방시설 → 점검표**: 기존 resultBadge 직행이 새 페이지에서도 동작
  (`linkFrom`으로 복귀 경로만 교정). 회차 종료 건은 `overview.canEdit=false`가 최종 심판
  (배지의 `canInputResult`(`:199`)가 이미 AND — 신규 코드 없음).
- **S5-4** 드로어(`inspection-sheet-client.tsx`)에도 같은 직행 링크를 둘지는 **구현 중 실측 후 결정**
  — 드로어는 현장용이라 이탈 링크가 오히려 방해일 수 있다(보류 시 사유 기록).

### S6 — respondedNotInstalled 원클릭 수리

- **S6-1** PlanForm14 resultMarks memo(`:182-197`)가 이미 부르는 `rollUpForm3Results`의
  `axisWarnings`(현재 버려짐)를 보존. 경고 있으면 표 위 amber 배너:
  「대장 미체크인데 점검표 응답 있음 N건(설비명…) — [모두 설치로 체크]」.
- **S6-2** 버튼은 해당 코드들 `installed=true` + `markDirty()`만 — **저장은 기존 [저장] 버튼**
  (저장규칙 단일 유지). 어휘는 `report9-assemble.ts:616-618` 경고와 통일.
  1.4·새 페이지 양쪽에서 공짜로 동작.
