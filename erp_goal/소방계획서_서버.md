### 0-C. 보안그룹 80·443 — ✅ 조치 불필요 (2026-08-24 실측 완료)

80·443 **둘 다 이미 열려 있다.** 가비아 콘솔에서 규칙을 추가할 필요가 없다.

| 프로토콜 | 포트 | 외부 실측 |
|---|---|---|
| TCP | 80 | HTTP 200 `PORTTEST_OK`, connect 22ms |
| TCP | 443 | HTTP 200 `PORTTEST_OK`, connect 21ms |
| TCP | 8080 | 8초 타임아웃 (음성 대조군) |

#### 포트 개방을 재확인해야 할 때 — 리스너부터 세션에서 떼어낼 것

이 항목은 한 번 **오진**했다. 처음엔 "80 = 상단 차단"으로 판정했는데,
원인은 방화벽이 아니라 **측정용 리스너가 이미 죽어 있던 것**이었다.
`ssh ... 'timeout 60 python3 -m http.server 80'`로 띄운 리스너는
**ssh 세션이 끝나는 순간 SIGHUP으로 함께 죽는다.**
서버 안에서 본 `ss`의 LISTEN은 그 시점엔 이미 과거의 사실이고,
외부가 받은 **즉시 RST는 차단이 아니라 "리스너 없음"의 정상 응답**이다.

두 원인은 **응답 모양으로 구분된다**:

| 관측 | 의미 |
|---|---|
| 긴 타임아웃 (8080의 8초) | 방화벽이 SYN을 **드롭** |
| 0초 RST | **리스너 부재** (방화벽은 통과했다) |
| HTTP 200 | 열림 |

올바른 절차:

```bash
# 1) 세션에서 분리해 띄운다
cd /tmp/porttest && sudo setsid nohup timeout 300 \
  python3 -m http.server 80 --bind 0.0.0.0 >/tmp/port80.log 2>&1 </dev/null &

# 2) SID가 ssh 세션과 다른지 확인 (같으면 분리 실패)
ps -eo pid,ppid,sid,cmd | grep http.server

# 3) ssh를 끊고, 재접속해 아직 살아 있는지 본 뒤에 외부에서 측정
# 4) 정리는 PID 지정으로 — pkill 금지 (아래)
sudo kill -TERM <pid>
```

- ⚠ `pkill -f 'http.server 80'`은 **자기 셸 명령줄까지 매칭해 ssh 세션을 죽인다** (exit 255)
- ⚠ PowerShell 5.1은 native exe 인자의 **작은따옴표 안에 있는 큰따옴표까지 삭제**한다.
  `grep -F ":80 "`가 `grep -F :80`이 돼 bash 구문 오류로 죽는다 — 원격 명령에 큰따옴표를 쓰지 말 것.
- 서버측 필터는 무죄로 확인됨: `iptables INPUT policy ACCEPT`·규칙 0개·Docker FORWARD 체인뿐·ufw inactive

## 4. 1단계 — 서버 기본 셋업

```bash
sudo apt update && sudo apt -y upgrade
sudo apt -y install git curl ca-certificates

# 스왑 2GB — 4GB RAM에서 Next 빌드 OOM 방지 (구 서버와 동일 구성)

sudo mkswap /swapfile && sudo swapon /swapfile

# 시간대 — 크론이 KST 기준으로 등록돼 있다
sudo timedatectl set-timezone Asia/Seoul

# Docker 공식 저장소 (Ubuntu 22.04 = jammy, VERSION_CODENAME이 자동 해석)
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt update && sudo apt -y install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

**선택 — `ubuntu` 계정 구성** (구 서버는 root 로그인 차단 + ubuntu 계정이었다):


> 되는 것을 확인한 뒤에** 적용한다. 순서를 바꾸면 스스로 잠긴다.

1. **`ACCOUNT_ENC_KEY`가 출처마다 다르다** — 백업 `5e6562a8…` vs `.env.local` `f1704eaa…`.

   실측 판정은 불가. VPS가 실제로 돌던 백업 값으로 고정했다.

3. **`NEXT_PUBLIC_*`는 빌드타임에 번들로 박힌다.** compose의 `env_file`은 런타임 전용이라
   이것만으로는 부족한데, `.dockerignore`가 **없어서** `COPY . .`로 `.env.production`이

`node:20-alpine`은 **떠다니는 태그**다. 베이스가 Alpine 3.23.4로 올라가면서 `font-nanum`이
저장소에서 사라졌다. **코드는 그대로인데 바깥이 움직여서** 깨진 것이다.

- 조치함(1차, 2026-08-24): `font-noto-cjk`로 교체. `static-map-compose.ts:101`의 체인이
  `Malgun Gothic, NanumGothic, Noto Sans CJK KR, sans-serif`라 **3순위로 이미 지목**하고 있어
  코드 변경 없이 맞물렸다
- ✅ **조치함(2차, 같은 날) — 폰트를 저장소로 들여왔다.** 1차는 임시방편이었다. 배포판
  패키지 **이름**에 기대는 한, 베이스를 옮길 때마다(=Node EOL 전환 때마다) 같은 지뢰를
  다시 밟는다. `erp/assets/fonts/`에 NanumGothic Regular·Bold(4.1MB, OFL 1.1)를 넣고
  `COPY`로 설치한다 — 이제 Alpine이 몇이든 Node가 몇이든 폰트는 불변이다.
  패밀리명이 `NanumGothic`이라 체인 **2순위에 이름으로** 맞물린다(sans-serif로 흘러
  '우연히' 렌더되는 게 아니다). `font-noto-cjk`(100MB대)가 빠져 이미지도 가벼워졌다
- ✅ **베이스 이미지 고정 완료** — `ARG NODE_IMAGE=node:20-alpine3.23`으로 3스테이지 단일 원천화.
  **Alpine 마이너까지 고정**하면 패키지 이름·가용성이 안정되면서 그 안의 패치는 계속 받는다
  (다이제스트 고정은 패치까지 얼려서 과했고, 태그 방치는 이번처럼 깨진다 — 그 중간)
- ✅ **커밋·푸시 완료 `6d4c408`** (게이트 통과: 격리 빌드 + INV 15건 0위반).
  서버 작업트리도 `git checkout` + `git pull`로 정리 — **정리 전후 md5 동일**이라
  현재 돌고 있는 이미지가 저장소 소스와 정확히 일치한다
- ✅ **해소 — Node 20 → 24 전환.** 종전 권고(v22)는 **정정한다.** 2026-08 기준 v22는 이미
  Maintenance(보안 수정만)에 EOL 2027-04-30이라 여덟 달 뒤 같은 작업을 반복하게 된다.
  v24(Krypton)는 Active LTS, EOL 2028-04-30. `next@16.2.9`는 `>=20.9.0`(상한 없음),
  `sharp@0.34.5`는 `>=21.0.0`이라 둘 다 통과한다. **개발 PC의 node도 v24라 이 전환으로
  개발·운영 런타임이 처음으로 일치한다.** v26은 2026-10-28에 LTS가 되지만 그때까지
  EOL 런타임을 더 굴리는 값이 더 크다 — 24로 가고 26은 다음 창에서.
- ⚠ **'마이너 고정이면 패치는 계속 받는다'가 20 라인에선 이미 거짓이었다.**
  Docker Hub 실측 `node:20-alpine3.23`의 `last_updated`는 **2026-04-15** — Node 20 EOL에
  맞춰 발행이 멎었다. 즉 §15.3이 자랑한 핀은 '고정'이 아니라 **동결**이었고, Node뿐 아니라
  그 안의 Alpine 패키지 패치까지 함께 멈춰 있었다. (대조: `node:24-alpine3.23`은 2026-08-03 갱신)
  **핀을 넣었다고 안심하지 말 것 — 그 태그가 아직 발행되고 있는지가 별개의 축이다.**
- ✅ **Gotenberg·Caddy도 고정.** `gotenberg/gotenberg:8`은 떠다니는 포인터였는데,
  **한글 노출은 앱 이미지보다 여기가 크다** — 별지 서식 6종 PDF가 전부 이 컨테이너의
  폰트로 찍힌다. §15.1의 '한글 폰트 30종'은 그날의 8.x에 대한 실측이지 다음 pull에 대한
  보장이 아니다. 운영·스테이징 모두 `8.36.0`, Caddy는 `2.11.4-alpine`

#### 폰트 검증은 '설치됐는가'가 아니라 '찍히는가'로 할 것

`apk add` 성공은 두부(□) 렌더를 배제하지 못한다. 이번엔 앱 컨테이너 안에서 실제로
SVG를 래스터화해 PNG를 받아 **눈으로 봤다**(`fonttest.mjs` 패턴).

⚠ **잉크 픽셀 수로는 판정할 수 없다.** 한글 체인과 '한글 없는 폰트' 대조군의 어두운 픽셀이
`2376`으로 **완전히 같았다** — fontconfig가 글자 단위로 폴백하기 때문에 대조군도 한글로
렌더된 것이었다. 두부도 잉크를 만들므로 수치는 두 경우를 구분하지 못한다.

✅ **그 육안 판정을 코드로 옮겼다** — `erp/scripts/assert-korean-glyphs.mjs`.
Dockerfile runner가 `RUN`으로 걸어 **폰트가 깨지면 이미지가 아예 만들어지지 않는다.**
pre-push와 `test:all`은 환경 무관한 파일 축만 본다(sha256·패밀리명·글리프 커버리지).

⚠ **첫 설계는 항진명제였고 변이 검사가 잡았다.** '두부는 코드포인트와 무관하게 같은
사각형'이라 보고 `'가가가'`와 `'가나다'`의 래스터 동일성으로 판정하려 했는데, **그 전제가
틀렸다.** pango는 글리프가 없으면 **코드포인트 16진수가 박힌 hexbox**를 그리므로
가(AC00)·나(B098)·다(B2E4)가 서로 달라져 **두부인데도 통과한다.**

채택한 판별자는 **구조**다. hexbox는 닫힌 사각 테두리라 잉크 bbox의 맨 윗줄이 꽉 찬다:

| | 윗줄 잉크비율 |
|---|---|
| 실제 한글 가·나·소·힣 | 0.079 ~ 0.086 |
| hexbox (U+100000) | **0.993** |

12배 분리라 임계 0.5는 두 군집 어느 쪽에서도 멀다. 게다가 검사 안에 **양성 대조군**이
들어 있어, 미할당 코드포인트가 '정상 글리프처럼' 보이면 판별자가 죽었다고 스스로 알린다.

⚠ **검사를 짤 때 겪은 함정 둘** — ①도구가 소스에 쓴 PUA 문자를 조용히 **탈락**시켜 빈
문자열을 렌더했다(리터럴도 `\u` 이스케이프도). `String.fromCodePoint`로만 만들 것.
②Windows는 BMP PUA(U+E000~F8FF)를 **Segoe 아이콘 폰트가 실제 글리프로 덮는다** —
'미지원 문자' 표본이 미지원이 아니었다. 평면16(U+100000)을 쓸 것.

#### VPS 실측 — 이미지 안에서 처음 돈 결과 (2026-08-24)

```
[축 2] ✅ fc-list :lang=ko — 1종   (font-noto-cjk 30종이 빠지고 우리 폰트만 남았다)
       ✅ fc-match NanumGothic → /usr/share/fonts/nanum/NanumGothic-Regular.ttf
[축 3] ✅ 대조군 U+100000 hexbox 윗줄비율 1.000   ← 판별자가 Alpine에서도 살아 있다
       ✅ 가 0.072 / 나 0.077 / 소 0.064 / 힣 0.081   (Windows 실측 0.079~0.086과 같은 군집)
```

**한글은 실제로 찍힌다.** 대조군이 정확히 `1.000`으로 나온 게 중요하다 — 임계 0.5가
두 군집 사이 빈 공간에 있음을 실환경이 확인해 줬다.

🐛 **그런데 첫 빌드는 실패했다 — 검사가 자기 환경을 잘못 가정한 내 버그였다.**
축 1b(Dockerfile 규약)·1c(compose 태그)는 **저장소 축**인데 조건 없이 돌아서, runner
이미지 안에 그 파일들이 없다는 이유로 3건 실패를 냈다(runner는 스크립트만 COPY한다).
폰트는 멀쩡한데 **멀쩡한 운영 빌드가 섰다.**
- 고친 방식: `--files-only`(저장소 축)와 기본(이미지 축)으로 **축 자체를 나눴다.**
- ⚠ **'파일이 없으면 통과'로 무마하지 않았다** — 그러면 저장소에서도 가드가 사라져
  Dockerfile을 지우거나 이름을 바꾼 회귀를 놓친다. 조용한 통과보다 축 분리가 옳다.
