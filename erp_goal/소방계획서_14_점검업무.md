## 1. 배경·결정사항

### 1-1. 점검 결과 (#10)
"다른 고객에서 복사"는 전체 복사가 아니었다. 실제 커버리지는 4곳뿐:
- 1.1 계획서 정보 패널 — 7개 필드(수신기위치·구조·지붕·급수·운영 평일/휴일·보험사), 빈 칸만
- 1.5 피난·방화 / 1.6 기타시설 / 1.11 훈련·교육 — `SectionCopyButton` 칩 (서버 화이트리스트 `COPYABLE_SECTION_KEYS` = evacFire·etcFacility·training 3개)

#6에서 지적된 "2장·3장 칩 없음"은 버그가 아니라 미구현이었다. 또한 1.5/1.6/1.11 복사는 **확인 없이 기존 입력 전체 덮어쓰기 + 즉시 DB 저장**이라 입력 유실 위험이 있었고, 1.5/1.6은 건물 고유 사실(계단 개소·수전용량·가스 위치 등)이라 타 고객 복사 자체가 데이터 오염이었다.

### 1-2. 결정 (2026-08-10 사용자 확정)
1. **"다른 고객에서 복사" 전면 폐지** — 칩 4곳 + 서버 액션 + 컴포넌트 삭제 (A안, 반영 완료)
2. **공통 서술 라이브러리 도입 — pull 방식** (#11): 서술형 섹션만 공통 항목에서 선택해 가져온다
3. **push(라이브러리 → 고객 일괄 반영) 제외**: 라이브러리 수정이 이미 생성·제출된 HWP/PDF와 소리 없는 불일치를 만들기 때문. 후속 과제로만 남긴다 (§7)
4. **별도 라이브러리 관리 페이지 없음**: 등록·이름변경·삭제 전부 각 서식 안에서 처리 (§4)

## 2. 대상 섹션 매핑 (#11 목록 → 실제 저장 키)

저장소는 전부 `fire_plan_forms.sections` JSONB. 라이브러리 대상은 **서술·템플릿 성격의 필드만** — 고객 고유 값(인원·월 선택·실시 기록)은 제외한다.

| 서식 | 섹션 키 | 라이브러리 대상 | 제외 (고객 고유) |
|---|---|---|---|
| 1.11 훈련·교육 | `training` | `scenario`·`scenarioType`(시나리오), `details`(차수별 세부계획 서술) | `headcount`·`eduMonths`·`drillMonths`·`records`(실시 결과) |
| 1.12 화기취급 감독 | `fireworkLog` | 행 템플릿(work·measure 서술) | date·place·supervisor |
| 1.13 소방시설 공사·정비 | `constructionLog` | 행 템플릿(content 서술) | date·facility·company |
| 1.14 화재예방·홍보 | `promoLog` | 행 템플릿(method·content) | date·target |
| 1.15 피해 복구 | `recoveryLog` | 행 템플릿(damage·recovery) | date·cost |
| 2장 팀별임무 2.5~2.13 | `brigadeTeams` | 7팀 Record 전체 (command·contact·extinguish·evacuate·rescue·protect·initial) | `brigadeGeneral.type`(편성 유형), 2.2 편성표(`fire_brigade_members`) |
| 3.4 피난유도 절차·경로 | `evacPlan` | `procedure`(절차 서술)·`assembly`(집결지 문구) | `routes`(층별 경로)·`mapImage` — 건물 고유 |
| 3.6 피난약자 유형별 방법 | `vulnerableMethods` | 6유형 Record 전체 (노인·어린이·영유아·임산부·장애인·기타) | — |

기존 코드 프리셋(1.11 `SCENARIO_PRESETS` 주택형/상가형/공장형, 2장 팀별 `preset`, 3.6 `METHOD_PRESETS`)은 **"기본 제공 항목"으로 존치** — 라이브러리는 그 위에 사용자 정의 변형을 쌓는 용도.

## 3. 저장 설계 — 마이그레이션 119 `plan_text_library`

```sql
-- 119_plan_text_library.sql
CREATE TABLE IF NOT EXISTS plan_text_library (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  section_key TEXT NOT NULL,              -- §2의 섹션 키 (training·fireworkLog·…·vulnerableMethods)
  title       TEXT NOT NULL,              -- 항목 이름 (예: "아파트용 훈련 시나리오")
  body        JSONB NOT NULL DEFAULT '{}',-- 섹션별 부분 값 (§2 '라이브러리 대상' 필드만)
  sort_order  INT  NOT NULL DEFAULT 0,
  is_active   BOOLEAN NOT NULL DEFAULT TRUE,
  updated_by  UUID REFERENCES profiles(id) ON DELETE SET NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_plan_text_library_section ON plan_text_library (section_key, is_active, sort_order);
ALTER TABLE plan_text_library ENABLE ROW LEVEL SECURITY;
-- 접근은 서버 액션(createAdminClient)만 — 096_fire_plan_forms.sql 관례와 동일
```

- 관례: `096_fire_plan_forms.sql` 패턴 (IF NOT EXISTS, RLS enable, ON DELETE SET NULL)
- 삭제는 `is_active=false` 소프트 삭제 — 가져간 고객 데이터에는 영향 없음(pull 시점 복사이므로 참조 없음)
- 대안 검토: 프리셋처럼 Storage JSON(`fire-plans` 버킷 `_presets/*.json` 패턴)도 가능하나, 동시 편집·수정 이력·불변식 검사에 약해 **테이블 채택**

## 4. UI 설계 — 관리 페이지 없음, 서식 안에서 전부 처리

각 대상 서식 헤더(§2의 8개 카드)에 칩 2개를 추가한다. 기존 `SectionCopyButton` 자리(우측 `ml-auto`)를 그대로 쓴다.

### 4-1. [공통에서 가져오기]
1. 클릭 → 해당 `section_key`의 활성 항목 리스트 팝오버 (이름 + 수정일, 여러 항목 중 선택 — #11 "여러 리스트에서 선택" 요구 반영)
2. 항목 선택 → **폼 상태에만 채움. DB 저장하지 않음** — 사용자가 검토 후 [저장]을 눌러야 반영
   - 구 복사 기능의 "즉시 저장 덮어쓰기" 문제를 설계로 차단
   - `dirty=true`로 표시해 미저장 이동 확인창(unsaved-nav)이 정상 작동
3. 해당 필드에 기존 입력이 있으면 인라인 확인("기존 서술을 덮어씁니다") 후 적용
4. §2 '라이브러리 대상' 필드만 병합 — 고객 고유 필드(인원·일자·기록)는 건드리지 않음
5. 적용 필드는 앰버 하이라이트 + "'{항목명}'에서 가져옴" 툴팁 (1.1 [추천값 채우기]의 `suggested` 패턴 재사용)

### 4-2. [공통으로 등록]
1. 클릭 → 이름 입력(기본값: "{고객명} {서식명}") → 현재 폼의 '라이브러리 대상' 필드만 추출해 저장
2. 같은 이름이 있으면 "덮어쓰기 / 새 항목" 선택
3. 가져오기 팝오버 안에서 항목별 ✏(이름변경)·🗑(삭제, is_active=false) 제공 → **별도 관리 화면 0개**

### 4-3. 컴포넌트
`erp/src/components/customers/library-text-button.tsx` 신설 (삭제된 section-copy-button.tsx의 팝오버 골격 참고). props: `customerId · sectionKey · sectionLabel · extract()`(폼→body) · `onApply(body)`(body→폼, 저장 없음).
